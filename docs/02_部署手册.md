# LinkMind 部署手册

> 版本：v2.0（2026-11-27）
> 适用架构：`backend/app`（FastAPI）+ `frontend/src`（React）+ PostgreSQL 17
> 权威参考：[15_API接口列表.md](./15_API接口列表.md)、[19_数据库设计.md](./19_数据库设计.md)、[18_后端工程结构设计.md](./18_后端工程结构设计.md)

## 一、部署架构与前提

### 1.1 服务组成

| 服务 | 镜像/构建 | 端口 | 职责 |
|------|-----------|------|------|
| `linkmind-web` | `frontend/Dockerfile`（Node 构建 + nginx） | 宿主机 `8080` → 容器 `80` | 托管前端静态资源；`/api/` 反代到后端；`/healthz` 健康检查 |
| `linkmind-backend` | `backend/Dockerfile` | `8000:8000` | FastAPI、服务端 Git CLI、数据库访问 |
| `postgres` | `pgvector/pgvector:pg17` | 宿主机 `5432` → 容器 `5432` | 事实主库，保存 5 张业务表 |
| `neo4j` | `neo4j:5.26.0` | `7474` / `7687` | **可选**，仅供 `/api/v1/health/neo4j` 连通性检查 |

数据流：

```
浏览器 → nginx（8080）
           ├─ 静态资源（React SPA，HashRouter）
           └─ /api/* → linkmind-backend:8000 → PostgreSQL 17
                                             └→ KNOWLEDGE_ROOT 内的真实 Git 仓库
```

### 1.2 前置要求

| 场景 | 要求 |
|------|------|
| Docker Compose 部署 | Docker 20.10+、Docker Compose v2；建议 4GB+ 内存 |
| 本地开发 | Python 3.12+、Node.js 20.x+ / npm 10.x+、系统 `git` |
| 数据库 | PostgreSQL 17（Compose 已内置） |
| 知识仓库 | `KNOWLEDGE_HOST_PATH` 必须是宿主机上**真实存在且可写**的目录，Git 提交/合并会写回该目录 |

### 1.3 关键约束

- 容器内的后端**不读取** `backend/.env`，环境变量必须由 Compose 注入。
- 宿主机 shell 中若已存在 `POSTGRES_USER`、`POSTGRES_PASSWORD`、`POSTGRES_DB`、`POSTGRES_PORT`，会覆盖 Compose 默认值；以 `docker compose config` 的输出为准。
- 前端生产环境缺省使用同源 `/api/v1`，由 nginx 反代；无需为 SPA 配置额外的服务端路由。

## 二、Docker Compose 部署

### 2.1 准备环境变量

```bash
# 在项目根目录执行
cp deploy/.env.example deploy/.env
```

编辑 `deploy/.env`，至少确认以下项：

| 变量 | 建议 |
|------|------|
| `SECRET_KEY` | 生产必须替换为高熵随机值（≥32 字节），不要使用默认值 |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | 按实际设置；改库名后无需改 `DATABASE_URL`，Compose 会自动拼接 |
| `POSTGRES_PORT` | 宿主机端口冲突时修改 |
| `FRONTEND_PORT` | 默认 `8080`，冲突时修改 |
| `CORS_ORIGINS` | 填写实际前端访问源，多个用逗号分隔；生产不要使用 `*` |
| `ALLOW_ANONYMOUS` | 默认 `true`；关闭前必须先具备 Token 签发与注入方案 |
| `KNOWLEDGE_HOST_PATH` | 知识仓库目录的宿主机绝对路径或相对 `deploy/` 的路径 |
| `GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL` | 用于服务端 Git 提交身份 |

核对最终配置（尤其是被宿主机环境变量覆盖的值）：

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml config
```

### 2.2 构建并启动

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build
```

查看状态与日志：

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps
docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs -f linkmind-backend
docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs -f linkmind-web
```

### 2.3 访问地址

| 服务 | 地址 |
|------|------|
| 前端页面 | `http://localhost:8080/` |
| 后端 API 根 | `http://localhost:8000/api/`（业务接口前缀 `/api/v1`） |
| Swagger 文档 | `http://localhost:8000/docs` |
| 前端健康检查 | `http://localhost:8080/healthz` |
| PostgreSQL | `localhost:5432` |
| Neo4j Browser（可选） | `http://localhost:7474` |

将 `localhost` 替换为实际服务器地址即可。

### 2.4 健康检查

```bash
# 前端 nginx（返回 ok）
curl http://localhost:8080/healthz

# 后端总健康检查
curl http://localhost:8000/api/v1/health

# PostgreSQL 连通性
curl http://localhost:8000/api/v1/health/postgres

# Neo4j 连通性（可选组件）
curl http://localhost:8000/api/v1/health/neo4j
```

Compose 内置健康检查：

- `postgres`：`pg_isready`；
- `linkmind-backend`：请求 `http://localhost:8000/api/v1/health`；
- `linkmind-web`：请求 `http://localhost/healthz`；
- `neo4j`：`cypher-shell ... 'RETURN 1'`。

`docker compose ps` 中服务状态应为 `healthy`。

### 2.5 数据库初始化与迁移

当前数据库为 5 张业务表：`git_repos`、`git_actions`、`maps`、`nodes`、`props`，详见 [19_数据库设计.md](./19_数据库设计.md)。

#### 空数据卷：自动执行初始化 SQL

Compose 将 `backend/migrations/001_init.sql` 挂载到 PostgreSQL 容器的 `/docker-entrypoint-initdb.d/001_init.sql`。该脚本**只在数据卷为空、容器首次初始化时执行一次**。

#### 已有数据卷：使用 Alembic

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  exec linkmind-backend python -m alembic upgrade head
```

- `linkmind-backend` 启动命令会先执行 `python -m alembic upgrade head`；数据库尚未就绪时忽略失败并降级启动。
- 基线版本：`0001_baseline`。
- 校验模型与库结构是否漂移：

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  exec linkmind-backend python -m alembic check
```

#### 核对表清单

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\dt"'
```

应看到 5 张业务表与 `alembic_version`；初始化 SQL 已写入版本 `0001_baseline`，因此随后执行 `alembic upgrade head` 为空操作，不会重复建表。

#### 可选种子数据

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  exec linkmind-backend python -m app.db.seed
```

仅在 `maps` 为空时插入 1 张地图、2 个节点、2 个属性。

### 2.6 停止与清理

```bash
# 停止服务，保留数据卷
docker compose --env-file deploy/.env -f deploy/docker-compose.yml down

# 停止并删除数据卷（会清空 PostgreSQL/Neo4j 数据，仅在确认后使用）
docker compose --env-file deploy/.env -f deploy/docker-compose.yml down -v
```

## 三、环境变量说明

`deploy/.env.example` 为完整模板：

| 变量 | 默认值 | 说明 |
|------|--------|------|
| `POSTGRES_USER` | `linkmind` | 数据库用户 |
| `POSTGRES_PASSWORD` | `linkmind` | 数据库密码，生产必须修改 |
| `POSTGRES_DB` | `linkmind` | 数据库名 |
| `POSTGRES_PORT` | `5432` | 宿主机映射端口 |
| `FRONTEND_PORT` | `8080` | 前端 nginx 宿主机端口 |
| `SECRET_KEY` | `change-me-to-a-random-secret-at-least-32-bytes` | JWT 签名密钥，生产必须替换 |
| `JWT_ALGORITHM` | `HS256` | JWT 算法 |
| `JWT_EXPIRE_MINUTES` | `120` | JWT 有效期 |
| `ALLOW_ANONYMOUS` | `true` | 匿名放行开关；当前无登录接口 |
| `CORS_ORIGINS` | `http://localhost:8080,http://127.0.0.1:8080` | 允许的前端源，逗号分隔 |
| `DB_POOL_SIZE` | `5` | SQLAlchemy 连接池大小 |
| `DB_MAX_OVERFLOW` | `10` | 连接池溢出上限 |
| `KNOWLEDGE_HOST_PATH` | `../docs/示例知识库` | 宿主机知识仓库目录，挂载到 `/app/knowledge` |
| `GIT_AUTHOR_NAME` | `LinkMind` | Git 提交用户名 |
| `GIT_AUTHOR_EMAIL` | `linkmind@local` | Git 提交邮箱 |
| `GIT_OPERATION_TIMEOUT` | `60` | Git 命令超时（秒） |
| `GIT_MAX_FILE_BYTES` | `262144` | 单文件内容上限（256KB） |

Compose 内部还会注入：

| 变量 | 值 | 说明 |
|------|----|------|
| `DATABASE_URL` | `postgresql+asyncpg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB}` | 后端连接串，使用服务名 `postgres` |
| `KNOWLEDGE_ROOT` | `/app/knowledge` | 容器内知识仓库根目录 |
| `NEO4J_URI` / `NEO4J_USER` / `NEO4J_PASSWORD` | `bolt://neo4j:7687` / `neo4j` / `password` | 仅健康检查使用 |

本地开发另可设置 `DB_ECHO`（是否打印 SQL）；后端配置读取 `backend/.env`。

## 四、本地开发部署

### 4.1 启动 PostgreSQL

推荐只启动数据库依赖：

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d postgres
```

如需验证 Neo4j 健康检查，再启动 `neo4j`；业务功能不依赖它。

### 4.2 启动后端（8000）

```bash
cd backend

# 安装依赖
uv sync --extra dev
# 或：.venv/bin/python -m pip install -e ".[dev]"

# 准备环境变量
cp .env.example .env
# 按需修改 DATABASE_URL / KNOWLEDGE_ROOT / SECRET_KEY / CORS_ORIGINS

# 数据库迁移
.venv/bin/python -m alembic upgrade head

# 启动
.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000
```

也可直接使用启动命令：

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

- 入口为 `backend/app/main.py`，API 前缀 `/api/v1`。
- 启动时探测 PostgreSQL；连接失败会降级启动，由具体接口返回明确错误。
- Swagger：`http://localhost:8000/docs`。

### 4.3 启动前端（5173）

```bash
cd frontend
npm install
npm run dev
```

访问 `http://localhost:5173/`。

### 4.4 前后端联调与 CORS

- 开发环境 API 基础地址见 `frontend/.env.development`：

  ```env
  VITE_API_BASE_URL=http://localhost:8000/api/v1
  ```

  此时浏览器直连后端，后端 `CORS_ORIGINS` 必须包含 `http://localhost:5173`。

- 将 `VITE_API_BASE_URL` 改为 `/api/v1` 时，请求走 `vite.config.ts` 的 `server.proxy`（`/api` → `http://localhost:8000`），同源无跨域。

- `CORS_ORIGINS` 使用逗号分隔的显式源列表；与 `allow_credentials=true` 搭配时不要使用 `*`。

### 4.5 测试与构建

```bash
# 后端测试
cd backend && .venv/bin/python -m pytest

# 接口联调（需后端与数据库已启动）
bash scripts/api-test.sh

# 前端单测、类型检查与构建
cd frontend && npm test
cd frontend && npm run typecheck && npm run build
```

## 五、数据备份与恢复

### 5.1 PostgreSQL 逻辑备份

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > linkmind-backup.dump
```

### 5.2 PostgreSQL 恢复

恢复前先停止后端写入，避免连接占用导致恢复失败：

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml stop linkmind-backend

cat linkmind-backup.dump | \
  docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists'

docker compose --env-file deploy/.env -f deploy/docker-compose.yml start linkmind-backend
```

建议定期做恢复演练：在独立环境或临时数据库中导入备份，核对 5 张业务表的数据量后再投入生产使用。

### 5.3 知识仓库备份

`KNOWLEDGE_HOST_PATH` 指向的是宿主机上的真实 Git 仓库目录，需单独纳入备份。以目录 `/srv/linkmind/knowledge` 为例：

```bash
tar czf linkmind-knowledge.tar.gz -C /srv/linkmind/knowledge .
```

实际操作时替换为 `deploy/.env` 中 `KNOWLEDGE_HOST_PATH` 对应的目录。

### 5.4 说明

- 优先使用 `pg_dump`/`pg_restore` 做跨版本、跨机器迁移。
- 直接复制数据卷属于物理备份，必须停库后操作，且 PostgreSQL 大版本不一致时不可直接复用。
- Git 运行状态不落库，每次读取实时执行 Git 命令；备份数据库不会丢失仓库历史，仓库历史由 Git 目录自身保存。

## 六、升级流程

1. 备份 PostgreSQL 与知识仓库目录（见第五章）。
2. 拉取新代码并核对 `deploy/.env.example` 是否新增变量。
3. 重新构建并启动：

   ```bash
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build
   ```

4. 后端容器启动时自动执行 `alembic upgrade head`；如启动日志显示迁移失败，手动执行：

   ```bash
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
     exec linkmind-backend python -m alembic upgrade head
   ```

5. 验证：`/healthz`、`/api/v1/health`、`/api/v1/health/postgres` 均正常，前端可加载地图列表。

## 七、Neo4j（可选组件）

当前版本中 Neo4j **不保存业务主数据**，业务接口也不依赖它，仅保留：

```bash
curl http://localhost:8000/api/v1/health/neo4j
```

用于连通性检查。因此：

- 不需要为业务部署 Neo4j；Compose 中的 `neo4j` 服务可按需停止或从编排中移除。
- 停止 Neo4j 后，`/api/v1/health/neo4j` 会返回失败，但地图、节点、属性、笔记与 Git 功能不受影响。
- 旧版“Neo4j 作为主存储”的部署步骤（包括以 Neo4j 数据目录为备份对象、依赖 Neo4j 索引初始化等）**仅适用于旧架构，已不适用于当前版本**。

如确需启用该可选组件，请保证 `NEO4J_URI=bolt://neo4j:7687`、账号密码与 `neo4j` 服务一致，且 `depends_on` 健康检查通过。

## 八、常见问题

### Q1：端口被占用

默认端口为前端 `8080`、后端 `8000`、PostgreSQL `5432`、Neo4j `7474` / `7687`。

```bash
# 查看占用
ss -lntp | grep -E '8080|8000|5432|7474|7687'

# 或
lsof -i :8080
```

处理方式：

- 修改 `deploy/.env` 中的 `FRONTEND_PORT` 或 `POSTGRES_PORT`；
- 后端 `8000` 目前固定在 Compose 中，如冲突需调整 `deploy/docker-compose.yml` 的端口映射；
- 停止占用端口的其他进程后再启动。

### Q2：环境变量被宿主机污染

**现象**：数据库用户名、密码、库名或端口与 `deploy/.env` 不一致。

**原因**：Compose 会读取宿主机同名环境变量，`POSTGRES_USER`、`POSTGRES_PASSWORD`、`POSTGRES_DB`、`POSTGRES_PORT` 会覆盖默认值。

**处理**：

```bash
# 查看最终解析结果
docker compose --env-file deploy/.env -f deploy/docker-compose.yml config

# 临时清除宿主机变量后再启动
env -u POSTGRES_USER -u POSTGRES_PASSWORD -u POSTGRES_DB -u POSTGRES_PORT \
  docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d
```

### Q3：初始化 SQL 没有执行

**原因**：`001_init.sql` 由 PostgreSQL 官方入口脚本执行，**仅在数据卷为空时运行一次**。已有 `pg-data` 卷不会重复执行。

**处理**：

- 已有数据卷：使用 Alembic 建表/升级

  ```bash
  docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
    exec linkmind-backend python -m alembic upgrade head
  ```

- 确认是空库且需要重新初始化：先备份，再执行 `down -v` 删除数据卷后重新启动（会清空全部数据，务必确认）。

### Q4：前端能打开但接口 502 / 数据为空

1. 检查后端健康状态：

   ```bash
   curl http://localhost:8000/api/v1/health
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps
   ```

2. 查看后端日志：

   ```bash
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs -f linkmind-backend
   ```

3. 确认 PostgreSQL 健康、迁移已执行、`maps` 表存在。
4. 若后端启动日志提示 PostgreSQL 连接失败，服务会降级启动，此时接口会返回明确错误而非空数据。

### Q5：浏览器报 CORS 错误

- 生产：`CORS_ORIGINS` 必须包含实际访问前端页面的源（协议 + 域名 + 端口）。例如 `https://linkmind.example.com`。
- 开发：直连后端时需包含 `http://localhost:5173`；使用 Vite 代理时同源无跨域。
- 不要将 `CORS_ORIGINS` 设为 `*` 同时保留 `allow_credentials=true`。

### Q6：鉴权相关

- 当前没有登录接口，`ALLOW_ANONYMOUS` 默认 `true`。
- 生产修改 `SECRET_KEY` 后，已签发的旧 Token 会失效。
- 关闭匿名（设为 `false`）前，必须先确定 Token 的签发与注入方案，否则前端请求会被拒绝。

### Q7：Neo4j 健康检查失败

- 业务不受影响；仅在需要该检查项时启动 `neo4j` 服务。
- 检查 `NEO4J_URI` 是否为 `bolt://neo4j:7687`（容器内使用服务名），账号密码是否与 `NEO4J_AUTH` 一致。

### Q8：Git 提交或合并失败

- 确认 `KNOWLEDGE_HOST_PATH` 真实存在且容器内可写；
- 确认宿主机与容器内的 `git` 可用，远端地址与凭据有效；
- 查看 `linkmind-backend` 日志与 Git 动作审计记录；
- 仓库路径必须位于 `KNOWLEDGE_ROOT` 内，路径越界会被拒绝。

### Q9：`alembic check` 提示存在待删除的旧表

**原因**：从早期版本沿用的 `pg-data` 数据卷可能残留历史设计的 10 张表（`knowledge_repository`、`knowledge_map`、`map_node`、`node_property`、`document` 等）。应用不会读写这些表，`alembic check` 会把它们识别为“数据库中多出的表”。

**处理**：

- 应用功能不受影响；如确认旧表无数据或已备份，可人工清理后再执行 `alembic check`。清理前务必先 `pg_dump` 备份。
- 全新部署（空数据卷）只会有 5 张业务表 + `alembic_version`，不会出现该告警。历史表清单见 [19_数据库设计.md](./19_数据库设计.md) 第八节。
