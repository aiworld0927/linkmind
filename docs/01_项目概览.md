# LinkMind 知识地图项目概览

> 版本：v2.0（2026-11-27）
> 对应实现：`backend/app`（FastAPI）+ `frontend/src`（React）+ PostgreSQL 17
> 接口契约：[15_API接口列表.md](./15_API接口列表.md)
> 数据库设计：[19_数据库设计.md](./19_数据库设计.md)

## 一、产品定位

LinkMind 是一个**以知识地图为核心、以真实 Git 仓库为版本载体**的个人知识库系统。用户把知识组织成“地图 → 节点 → 属性/笔记”的层级结构，在画布上浏览、搜索和编辑；同时可以把知识仓库登记为真实 Git 仓库，在系统内完成状态查看、提交、拉取、推送与冲突处理。

产品要解决的问题：

- 用可视化地图替代零散目录，降低知识检索与回顾成本；
- 让笔记与知识结构绑定，而不是散落在孤立文档中；
- 把 Git 作为知识版本管理的真实底座，保留可审计的操作记录；
- 以单机、自托管、低依赖为优先，数据落在自有 PostgreSQL。

## 二、当前实现边界

### 2.1 已实现

| 能力 | 说明 |
|------|------|
| 知识地图管理 | 地图列表/搜索、新建、编辑、删除；首页展示节点数与属性数 |
| 地图整树读写 | 进入地图时读取整树，节点/属性变更后以服务端返回的整树刷新本地缓存 |
| 节点管理 | 新增、重命名、级联删除；支持多级父子层级与同级重名校验 |
| 属性/笔记管理 | 属性新增、编辑、删除；属性携带标签、备注、笔记正文、文档标记与文档路径 |
| 笔记编辑与阅读 | 基于 Vditor 的 Markdown 编辑与阅读；按 `mapId/nodeId/propId` 读取、保存 |
| 知识地图导入/导出 | 后端扫描 `KNOWLEDGE_ROOT` 目录导入并落库；导出由后端聚合全部地图 |
| Git 仓库管理 | 仓库登记/移除、状态、历史提交、动作审计 |
| Git 真实操作 | 勾选/全部提交、拉取（fetch + merge）、推送、冲突预览与解决、合并生命周期 |
| 健康检查 | `/api/v1/health`、`/health/postgres`、`/health/neo4j` |
| 数据持久化 | 知识地图、节点、属性、笔记全部写入 PostgreSQL，刷新页面不丢失 |

接口规模：**31 项业务接口 + 3 项健康检查**，路径前缀 `/api/v1`。

### 2.2 未实现或不在当前范围

| 事项 | 现状 |
|------|------|
| 登录与用户体系 | **没有登录接口**；后端具备 JWT 校验配置，但 Token 签发/注入方案需生产环境自行确定 |
| 多用户与权限 | 未实现用户、角色、租户隔离 |
| 独立文档管理 | 无文档表；仅在属性上保留 `doc` / `doc_path` 标记，不提供文档内容 CRUD |
| 全文检索与向量检索 | 未实现；PostgreSQL 使用 pgvector 镜像但当前无向量列 |
| 图算法能力 | Neo4j 仅用于 `/health/neo4j` 连通性检查；聚类、最短路径、邻居展开等图查询不在当前业务范围 |
| 独立关系/依赖表 | 当前 5 张业务表中没有 link/edge 表，未提供关系 CRUD |
| 通用操作审计表 | 仅 `git_actions` 记录 Git 动作；无通用 operation_audit |
| UI 端到端自动化 | 未建设；当前以单元测试、接口联调和构建检查为主 |

### 3.3 分层与目录

- `backend/app/main.py`：FastAPI 实例、CORS、路由注册、全局异常、lifespan。
- `backend/app/api/v1/`：按模块拆分 `health`、`git`、`fs`、`mindmap`，模块内包含 `router`、`schemas`、`service`、`repository`、`models`。
- `backend/app/core/`：配置、鉴权、异常、统一响应、日志、分页。
- `backend/app/db/`：声明式基类、异步会话、种子数据。
- `backend/alembic/`：迁移环境与 `versions/0001_baseline.py`。
- `backend/migrations/001_init.sql`：与基线等价的空库初始化 SQL。
- `frontend/src/`：`pages`、`features`（mindmap/git）、`store`、`types`、`utils`、`config`、`data`。
- `deploy/`：`docker-compose.yml` 与 `.env.example`。

## 四、运行形态

### 4.1 开发环境

| 组件 | 地址/端口 | 说明 |
|------|-----------|------|
| 前端 | `http://localhost:5173` | Vite 开发服务器 |

### 4.2 生产环境（Docker Compose）

| 服务 | 端口 | 说明 |
|------|------|------|
| `linkmind-web` | 宿主机 `8080` → 容器 `80` | nginx 托管前端静态资源，并将 `/api/` 反代到 `linkmind-backend:8000` |

| `postgres` | `5432` | PostgreSQL 17 主库 |

## 五、关键流程

### 5.1 鉴权流程（当前无登录）

1. 后端通过 `Authorization: Bearer <JWT>` 解析身份，JWT 使用 `SECRET_KEY` 签发/校验。
2. `ALLOW_ANONYMOUS` 默认 `true`，无 Token 或 Token 无效时业务接口仍按匿名放行。
3. 当前没有登录、注册、Token 签发接口；生产若要关闭匿名，需要先确定 Token 由谁签发、如何注入前端。

### 5.2 Git 管理流程

1. 在 Git 管理页登记仓库：`fs_path` 是相对 `KNOWLEDGE_ROOT` 的目录，服务端校验路径不越界。
2. 状态查看实时执行 Git 命令，读取分支、上游、领先/落后、变更文件、暂存状态与冲突；运行状态不落库。
3. 提交：可勾选文件或全部提交；存在未解决冲突时禁止提交。
4. 拉取：`fetch --prune` + `merge --no-edit`；冲突时保留合并状态，进入冲突处理。
5. 推送：校验上游；非快进时提示先拉取。
6. 冲突处理：预览本地/远端内容，支持保留本地、保留远端或编辑自定义合并结果；之后可完成或放弃合并。
7. 审计：每次 Git 动作写入 `git_actions`（动作、说明、文件、成功与否），历史提交与动作记录可查询。

安全边界：仓库限定在 `KNOWLEDGE_ROOT`；Git 命令 `shell=False`；超时与单文件大小限制；路径穿越防护。

### 5.3 知识地图 CRUD

1. 应用启动时调用地图列表接口加载首页卡片。
2. 新建/编辑/删除地图调用对应接口，成功后刷新列表。
3. 进入某张地图时读取整树（地图 → 节点 → 属性）；节点或属性变更后，用服务端返回的整树替换本地缓存。
4. 地图中的虚拟根节点 `ROOT` 不单独落库：根节点即地图标题，重命名 `ROOT` 等价于更新地图标题；根节点不可删除。

### 5.4 节点与属性/笔记

- 节点：新增、重命名、级联删除；层级由 `parent_id` 递归构建，响应中的路径由服务层拼接。
- 属性：新增、编辑、删除；接口返回 `prop_id` 作为稳定主键，前端后续编辑/删除/读写笔记均以 `prop_id` 定位。
- 笔记：属性上的 `note_content`（Markdown）、`note_tags`、`note_remark`、`doc`、`doc_path`；笔记页按 `mapId/nodeId/propId` 读取与保存。
- 导入/导出：导入由后端扫描目录并落库；导出由后端聚合全部地图，前端直接下载结果。

## 六、数据模型概要

当前共 5 张业务表（另有 `alembic_version`）：

| 表 | 用途 | 关键关系 |
|----|------|----------|
| `git_repos` | Git 仓库登记 | 被 `git_actions`、`maps` 引用 |
| `git_actions` | Git 动作审计（不可变） | `repo_id` → `git_repos.id`，级联删除 |
| `maps` | 知识地图 | `repo_id` → `git_repos.id`，仓库删除后置空 |
| `nodes` | 地图节点 | `map_id` → `maps.id`；`parent_id` 自引用，均级联删除 |
| `props` | 节点属性/笔记 | `map_id` → `maps.id`；`node_id` 可空（空表示地图级/前端 ROOT） |

字段、索引、约束与迁移方式详见 [19_数据库设计.md](./19_数据库设计.md)。

## 七、与旧设计的差异

| 维度 | 旧文档描述 | 当前真实状态 |
|------|------------|--------------|
| 后端代码位置 | `backend/src`，入口 `src/main.py` | `backend/app`，入口 `backend/app/main.py` |
| 启动命令 | `cd src && python main.py` | `uvicorn app.main:app --host 0.0.0.0 --port 8000` |
| 主存储 | Neo4j 图数据库 | PostgreSQL 17 为唯一事实主库 |
| Neo4j 定位 | 业务主存储/图查询 | 可选组件，仅 `/api/v1/health/neo4j` 连通性检查 |
| 数据表 | 10 张表设计 | 实际 5 张业务表：`git_repos`、`git_actions`、`maps`、`nodes`、`props` |
| 前端持久化 | localStorage / 种子数据 | 全部经 API 落库 PostgreSQL；localStorage 仅保留瞬时 UI 状态 |
| 前端托管 | 由后端挂载 `frontend/dist` | 由独立 nginx 容器托管，宿主机端口 8080，`/api` 反代后端 |
| API 前缀 | `/api` | `/api/v1` |
| 鉴权 | 未明确 | 无登录接口，`ALLOW_ANONYMOUS` 默认 `true`，JWT 由 `SECRET_KEY` 签发 |

## 八、快速开始

```bash
# Docker Compose
cp deploy/.env.example deploy/.env
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build

# 本地开发
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d postgres
cd backend && .venv/bin/python -m alembic upgrade head
.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000

cd frontend && npm install && npm run dev
```

访问：开发 `http://localhost:5173`，生产 `http://localhost:8080`；API 文档 `http://localhost:8000/docs`。详细步骤见 [02_部署手册.md](./02_部署手册.md)。
