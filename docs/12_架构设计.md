# LinkMind 架构设计

> 文档依据：`backend/src`、`frontend/src`、`deploy/docker-compose.yml`、`backend/Dockerfile` 的当前实现。
> 本文只描述已落地的结构与能力；未实现或未接通的部分在「实现边界」中显式标注。

## 一、系统定位

LinkMind 是面向个人与团队的知识地图系统，提供三类核心能力：

| 能力 | 承载方式 |
|------|----------|
| 知识地图与笔记 | React + AntV X6 画布，按层级下钻；数据默认持久化到浏览器 `localStorage` |
| 知识文档与版本管理 | FastAPI 服务端调用真实 `git` CLI，对 `KNOWLEDGE_ROOT` 内的知识仓库执行状态查看、提交、拉取、推送与冲突处理 |
| 图谱查询与聚类 | 保留既有 Neo4j 业务路由（notes/links/graph/expand/search/cluster），Neo4j 作为派生图索引 |

PostgreSQL 是事实主库：`001_init.sql` 已定义知识仓库登记、知识地图/节点/属性/文档、审计与文档向量共 10 张表；当前 Git 模块已接入 `knowledge_repository` 与 `git_action`。Neo4j 不再承担主存储职责。

## 二、总体分层

```
┌──────────────────────────────────────────────────────────────┐
│ 前端 SPA（React 18 + TypeScript + Vite）                      │
│ HashRouter 路由壳：首页 / 脑图 / Git 管理 / 笔记               │
│ 页面 → features(git/notes) → components → zustand store → fetch    │
└──────────────────────────────┬───────────────────────────────┘
                               │ HTTP/JSON  /api/v1/*
┌──────────────────────────────▼───────────────────────────────┐
│ FastAPI 后端                                                  │
│ routes（HTTP/校验）→ services（业务/事务/编排）                │
│                   → repositories（SQL/数据访问）               │
│                   → models（Pydantic / SQLAlchemy ORM）        │
│                   → database（asyncpg / Neo4j driver）         │
└───────┬───────────────────┬───────────────────┬──────────────┘
        │                   │                   │
┌───────▼─────────┐ ┌───────▼──────────┐ ┌──────▼───────────────┐
│ PostgreSQL 17   │ │ Neo4j 5.26       │ │ 本地知识仓库（磁盘）  │
│ + pgvector 主库 │ │ 派生图索引       │ │ KNOWLEDGE_ROOT 内    │
│                 │ │                  │ │ git CLI 真实操作      │
└─────────────────┘ └──────────────────┘ └──────────────────────┘
```

分层约束：

- 路由层不写 SQL，只做参数接收、依赖注入与响应封装。
- 服务层持有事务边界与业务规则，Git 服务不依赖 FastAPI / SQLAlchemy。
- 仓储层只接收 `AsyncSession`，不创建会话、不提交事务。
- 前端页面不直接调用 X6 实例，画布能力通过 `CanvasController` 注册到 store 后由工具栏消费。

## 三、运行时拓扑

`deploy/docker-compose.yml` 定义三个服务：

| 服务 | 镜像 / 构建 | 端口 | 关键配置 | 健康检查 | 依赖 |
|------|-------------|------|----------|----------|------|
| `neo4j` | `neo4j:5.26.0` | `7687`、`7474` | `NEO4J_AUTH=neo4j/password`；pagecache 512M，heap 1G | `cypher-shell -u neo4j -p password 'RETURN 1'`，10s 间隔、20 次重试、30s 启动宽限 | 无 |
| `postgres` | `pgvector/pgvector:pg17`，容器名 `linkmind-postgres` | `${POSTGRES_PORT:-5432}:5432` | `POSTGRES_USER/PASSWORD/DB` 默认均为 `linkmind`；`TZ=Asia/Shanghai` | `pg_isready -U linkmind -d linkmind`，10s 间隔、10 次重试、20s 启动宽限 | 无 |
| `backend` | 构建 `../backend` | `8000:8000` | `DATABASE_URL` 指向 `postgres:5432`；`NEO4J_URI=bolt://neo4j:7687`；`KNOWLEDGE_ROOT=/app/knowledge` | 请求 `http://localhost:8000/api/v1/health`，15s 间隔、10 次重试、20s 启动宽限 | `neo4j`、`postgres` 均 `service_healthy` |

数据与挂载：

| 挂载 | 说明 |
|------|------|
| `neo4j-data:/data`、`neo4j-logs:/logs` | Neo4j 数据与日志 |
| `pg-data:/var/lib/postgresql/data` | PostgreSQL 数据 |
| `../backend/migrations/001_init.sql:/docker-entrypoint-initdb.d/001_init.sql:ro` | 空库首次启动自动执行基线 DDL |
| `../frontend/dist:/app/frontend/dist:ro` | 后端以静态站点方式托管前端产物 |
| `${KNOWLEDGE_HOST_PATH:-../docs/示例知识库}:/app/knowledge` | 知识仓库根目录，必须可写（真实提交与合并） |

启动顺序：`postgres` / `neo4j` 健康 → `backend` 启动。后端 `lifespan` 中先初始化 Neo4j 索引，再初始化 PostgreSQL 连接；任一数据库不可用时仅记录告警并降级启动，由具体接口返回明确错误，不阻塞进程。

### 4.2 后端

```
backend/src/
├── main.py                     # 应用装配、路由注册、lifespan、静态资源托管
├── config/settings.py          # pydantic-settings 配置
├── database/
│   ├── pg.py                   # SQLAlchemy 2.x async engine/session
│   ├── neo4j_connection.py     # Neo4j driver 与连通性检查
│   └── init_indexes.py         # Neo4j 索引初始化
├── models/                     # Pydantic 模型（note/link/graph/git）+ ORM 模型
├── repositories/               # 数据访问（Neo4j 既有仓储 + PostgreSQL Git 仓储）

```

依赖方向固定为 `routes → services → repositories → models → database`；`services/git_service.py` 只依赖标准库、配置与异常类型，可独立单元测试。

## 五、关键架构决策（ADR）

### ADR-001 PostgreSQL 作为事实主库

- **背景**：既有实现以 Neo4j 存储笔记与关系，缺少强约束、审计与向量能力；知识仓库登记、文档元数据、操作审计需要关系型事务保障。
- **决策**：新增 PostgreSQL 17 + pgvector 作为主数据存储，通过 `backend/migrations/001_init.sql` 建立 10 张表；ORM 与 DDL 一一对应。
- **后果**：主数据具备唯一约束、外键级联、部分唯一索引与 GIN/BRIN/ivfflat 索引；业务路由需要逐步迁移到 PostgreSQL，当前仅 Git 登记与审计已接入。

### ADR-002 Neo4j 仅作派生图索引

- **背景**：既有 notes/links/graph/expand/search/cluster 路由直接依赖 Neo4j，短期内无法整体重写。
- **决策**：保留 Neo4j 作为关系查询、聚类与全文的派生索引；主数据定位改为 PostgreSQL。
- **后果**：两套存储并存，当前没有自动同步管道；Neo4j 中的数据视为可重建的派生数据，不应作为唯一事实来源。后续需要补齐同步与重建机制。

### ADR-003 Git 能力使用服务端真实仓库 + git CLI

- **背景**：原型使用 `localStorage` 假数据，无法反映真实版本状态。
- **决策**：`GitService` 通过 `subprocess.run` 调用系统 `git`，参数以列表传递且 `shell=False`，设置 `timeout=settings.GIT_OPERATION_TIMEOUT`，通过 `-c user.name/-c user.email` 注入提交身份，并设置 `GIT_TERMINAL_PROMPT=0`。
- **后果**：能力与真实 Git 一致，可用临时裸远端做集成测试；部署镜像必须安装 `git`；凭证由部署环境预配置，产品不提供凭证管理 UI。

### ADR-004 知识仓库限定在 KNOWLEDGE_ROOT

- **背景**：服务端执行 Git 命令存在越权访问产品代码或系统文件的风险。
- **决策**：登记路径以 `KNOWLEDGE_ROOT` 为根解析，拒绝绝对路径、`..` 与符号链接逃逸；每次操作前重新解析并校验目录存在。
- **后果**：所有 Git 操作被限制在知识目录内；产品工程仓库与知识仓库物理隔离；`DELETE /git/repos/{id}` 只删除登记，不删除文件。

### ADR-005 前端使用 HashRouter

- **背景**：前端产物由后端 `StaticFiles` 托管，静态服务器无法为任意深链接回退到 `index.html`。
- **决策**：使用 `react-router-dom` v6 的 `HashRouter`。
- **后果**：`#/`、`#/map/:datasetId`、`#/git`、`#/note` 可直接刷新；URL 带 `#`，不参与服务端路由。

### ADR-006 统一响应与业务异常体系

- **背景**：需要前后端稳定的错误契约。
- **决策**：成功响应统一为 `{code: 200, msg, data}`；业务异常继承 `BusinessError`（默认 400），`GitError(status_code, message)`、`NotFoundError(404)`、`ConflictError(409)`；`exception_handler` 将 `BusinessError`、请求校验错误、HTTP 异常与未捕获异常统一转换为 `{code, msg, data}`。
- **后果**：前端 `api.ts` 只按 `code === 200` 解包；Git 路由与健康检查通过异常处理器返回与 `code` 一致的 HTTP 状态码。部分既有 Neo4j 业务路由仍直接 `return error_response(code=500, ...)`，此时 HTTP 状态仍为 200，属于待统一的遗留行为。

### ADR-007 每仓库 asyncio.Lock 串行化

- **背景**：并发执行 `git add/commit/merge` 会破坏索引或产生竞态。
- **决策**：`git_registry_service` 维护进程级 `_LOCKS: dict[str, asyncio.Lock]`，按仓库 UUID 取锁；Git 同步调用通过 `run_in_threadpool` 执行，避免阻塞事件循环。
- **后果**：同仓库操作串行、不同仓库可并行；锁只在单进程内有效，多 worker/多副本部署时需外部锁。

### ADR-008 Git 动作写入 git_action 审计

- **背景**：需要追踪谁在何时对哪个知识仓库执行了什么操作及结果。
- **决策**：`GitRegistryService._execute` 在成功和业务失败时都写入 `git_action`；成功消息包含「冲突」时记 `ok=false`（拉取产生冲突属于未完成状态）。
- **后果**：动作记录与仓库视图一同返回，前端无需额外请求；审计写入与业务操作在同一会话中提交，审计失败会使操作报错。

## 六、横切关注点

| 关注点 | 现状 |
|--------|------|
| 配置 | `config/settings.py` 使用 `pydantic-settings`，读取 `backend/src/.env`，未知环境变量忽略（`extra="ignore"`） |
| 异常处理 | `middleware/exception_handler.py` 注册 4 类处理器；服务层只抛业务异常，不依赖 FastAPI |
| 参数校验 | 路由使用 Pydantic 模型与 `Query(ge/le)`；`GitCommitRequest`、`GitResolveRequest` 使用 `model_validator` 做跨字段校验 |
| 健康检查 | `/api/v1/health` 进程存活；`/health/neo4j`、`/health/postgres` 返回 `{connected, message}` |
| 日志与可观测性 | 使用标准库 `logging`，仅记录启动/降级/健康检查失败等关键事件；无指标、链路追踪、结构化日志与告警接入 |
| 跨域 | `CORSMiddleware` 允许全部来源、方法与请求头，且 `allow_credentials=True`；无认证体系 |
| 静态资源 | 若 `frontend/dist` 存在则挂载到 `/`，否则 `/` 返回提示 JSON；`src/static` 存在时挂载到 `/static` |
| 事务 | 请求级 `AsyncSession` 由 `get_session` 注入并在异常时回滚；服务层显式 `commit()` |

## 七、安全边界

| 风险 | 防护实现 | 边界说明 |
|------|----------|----------|
| 仓库路径穿越 | `resolve_repo_path()` 拒绝绝对路径与 `..`，`resolve()` 后必须位于 `KNOWLEDGE_ROOT` 内 | 符号链接解析后同样受 `is_relative_to` 约束 |
| Git 文件路径穿越 | `GitService._safe_rel()` 拒绝空值、`-` 开头、绝对路径、`..`、`.git` 首段，并做真实路径边界校验 | 所有文件参数统一经过该校验 |
| 命令注入 | 所有 Git 命令以参数列表执行，`shell=False`；不使用字符串拼接命令 | 提交信息作为 `-m` 的独立参数传入 |
| 文件大小 | `GIT_MAX_FILE_BYTES` 默认 262144（256KB）；冲突预览与自定义合并内容均受此限制，超限截断并标注或直接拒绝 | 仅覆盖 Git 冲突内容，不是通用上传限制 |
| 目录扫描越权 | `/fs/dirs`、`/fs/tree` 只允许 `KNOWLEDGE_ROOT` 内目录，跳过符号链接、隐藏目录与 `node_modules` 等 | 最大深度 20，单文件读取上限 256KB |
| 知识库与产品仓库隔离 | 知识仓库根目录独立挂载；产品代码仓库不注册、不执行 Git 操作 | compose 默认挂载 `../docs/示例知识库` |
| 凭证 | 由运行环境预置 SSH key / HTTPS 凭证；`GIT_TERMINAL_PROMPT=0` 禁止交互式询问 | 产品不保存、不展示凭证 |
| 认证授权 | 当前无用户体系，接口默认对可达网络开放 | 部署时需通过网络边界或反向代理保护 |

## 八、实现边界与已知缺口

以下内容与当前代码一致，文档不作能力假设：

1. **PostgreSQL 业务表尚未接入读写**：`knowledge_map`、`map_node`、`node_property`、`document`、`node_document_link`、`node_link`、`operation_audit`、`document_embedding` 已完成 DDL/ORM，但当前只有 `knowledge_repository` 与 `git_action` 被 Git 模块使用；画布数据仍保存在浏览器 `localStorage`。
2. **Neo4j 与 PostgreSQL 无同步管道**：既有业务路由仍直接读写 Neo4j，主库迁移尚未完成。
3. **仓库锁为单进程锁**：`_LOCKS` 不跨进程，多副本部署时同一仓库可能并发执行。
4. **无认证/权限/审计登录主体**：`operation_audit.actor` 默认 `local`，Git 动作无操作者字段。
5. **可观测性有限**：无指标、链路追踪、结构化日志与告警；仅标准库日志记录启动、降级与健康检查失败。
6. **Git 凭证不由产品管理**：依赖部署环境预置 SSH key / HTTPS 凭证，界面不提供凭证录入与校验。
