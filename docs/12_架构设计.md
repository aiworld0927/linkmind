# LinkMind 架构设计

> 文档依据：`backend/app`、`frontend/src`、`deploy/docker-compose.yml`、`backend/Dockerfile` 的当前实现。
> 本文只描述已落地的结构与能力；未实现或未接通的部分在「实现边界」中显式标注。

## 一、系统定位

LinkMind 是面向个人与团队的知识地图系统，提供三类核心能力：

| 能力 | 承载方式 |
|------|----------|
| 知识地图与笔记 | React + 自研 SVG 递归画布（`features/mindmap/MindCanvas.tsx`）；地图/节点/属性/笔记全部经 `/api/v1` 持久化到 PostgreSQL |
| 知识文档与版本管理 | FastAPI 服务端调用真实 `git` CLI，对 `KNOWLEDGE_ROOT` 内的知识仓库执行状态查看、提交、拉取、推送与冲突处理；登记与审计落 PostgreSQL |
| 运行时图数据 | Git 分支/领先落后/变更/冲突等状态每次实时执行 `git` 命令计算，不落库 |

PostgreSQL 17 是事实主库：Alembic 基线 `0001_baseline`（等价脚本 `backend/migrations/001_init.sql`）定义 5 张业务表：`git_repos`、`git_actions`、`maps`、`nodes`、`props`。Neo4j 5.26 为可选组件，仅用于 `/api/v1/health/neo4j` 连通性检查，不保存主数据、不参与业务接口。字段与迁移细节见 [19_数据库设计.md](./19_数据库设计.md)。

## 二、总体分层

```
┌──────────────────────────────────────────────────────────────┐
│ 前端 SPA（React 18 + TypeScript + Vite 5 + antd）             │
│ HashRouter：首页 / 脑图 / Git 管理 / 笔记                      │
│ pages → features(mindmap/git/notes) → store(zustand)          │
│       → utils/http.ts → /api/v1/*                             │
└──────────────────────────────┬───────────────────────────────┘
                               │ HTTP/JSON  /api/v1/*
┌──────────────────────────────▼───────────────────────────────┐
│ FastAPI 后端（backend/app）                                    │
│ api/v1 routers（HTTP/校验/统一响应）                           │
│   → services（业务规则/事务/Git CLI 编排）                     │
│   → repositories（SQLAlchemy 2.0 select/insert/update）        │
│   → models（各模块 ORM） → db/session（asyncpg）               │
│ core（config/security/exceptions/response）+ db               │
└───────┬───────────────────────────────────┬──────────────────┘
        │                                   │
┌───────▼─────────┐            ┌────────────▼──────────────────┐
│ PostgreSQL 17   │            │ 本地知识仓库（磁盘）           │
│ 5 张业务表       │            │ KNOWLEDGE_ROOT 内 git CLI 操作 │
└─────────────────┘            └───────────────────────────────┘
        ┌──────────────────────────────┐
        │ Neo4j 5.26（可选）            │
        │ 仅 /health/neo4j 连通性检查   │
        └──────────────────────────────┘
```

分层约束：

- 路由层不写 SQL，只做参数接收、依赖注入（`get_db`、`get_current_user`、`Pagination`）与响应封装。
- 服务层持有事务边界与业务规则；Git 服务通过 `run_in_threadpool` 执行同步 `git` 命令。
- 仓储层只接收 `AsyncSession`，不创建会话、不提交事务。
- 模型按业务模块就近定义：`api/v1/git/models.py`、`api/v1/mindmap/models.py`；不存在全局 ORM 模型文件。
- 前端页面不直接操作画布内部状态，画布交互统一经 `store/index.ts` 的 action。

## 三、运行时拓扑

`deploy/docker-compose.yml` 定义四个服务：

| 服务 | 镜像 / 构建 | 端口 | 关键配置 | 健康检查 | 依赖 |
|------|-------------|------|----------|----------|------|
| `neo4j` | `neo4j:5.26.0` | `7687`、`7474` | `NEO4J_AUTH=neo4j/password`；pagecache 512M，heap 1G | `cypher-shell -u neo4j -p password 'RETURN 1'`，10s 间隔、20 次重试、30s 启动宽限 | 无（可选组件） |
| `postgres` | `pgvector/pgvector:pg17`，容器名 `linkmind-postgres` | `${POSTGRES_PORT:-5432}:5432` | `POSTGRES_USER/PASSWORD/DB` 默认均为 `linkmind`；`TZ=Asia/Shanghai` | `pg_isready -U linkmind -d linkmind`，10s 间隔、10 次重试、20s 启动宽限 | 无 |
| `linkmind-backend` | 构建 `../backend` | `8000:8000` | `DATABASE_URL` 指向 `postgres:5432`；`KNOWLEDGE_ROOT=/app/knowledge`；JWT/CORS 由 compose 注入 | 请求 `http://localhost:8000/api/v1/health`，15s 间隔、10 次重试、20s 启动宽限 | `neo4j`、`postgres` 均 `service_healthy` |
| `linkmind-web` | 构建 `../frontend`（Nginx） | `${FRONTEND_PORT:-8080}:80` | 静态站点 + 反向代理 `/api` 到 `backend:8000` | `wget -qO- http://localhost/healthz` | `linkmind-backend` |

端口约定：

| 场景 | 端口 |
|------|------|
| 后端 API | 8000（`/api/v1`） |
| 前端开发服务器 | 5173（Vite，`/api` 代理到 8000） |
| 生产 web 容器 | 8080（Nginx） |
| PostgreSQL | 5432 |
| Neo4j（可选） | 7474（HTTP）、7687（Bolt） |

数据与挂载：

| 挂载 | 说明 |
|------|------|
| `neo4j-data:/data`、`neo4j-logs:/logs` | Neo4j 数据与日志（可选） |
| `pg-data:/var/lib/postgresql/data` | PostgreSQL 数据 |
| `../backend/migrations/001_init.sql:/docker-entrypoint-initdb.d/001_init.sql:ro` | 空库首次启动自动执行基线 DDL |
| `${KNOWLEDGE_HOST_PATH:-../docs/示例知识库}:/app/knowledge` | 知识仓库根目录，必须可写（真实提交与合并） |

启动顺序：`postgres` / `neo4j` 健康后 `linkmind-backend` 启动，容器命令先执行 `alembic upgrade head`（失败不阻塞），再 `uvicorn app.main:app --host 0.0.0.0 --port 8000`。后端 `lifespan` 只探测 PostgreSQL，不可用时记录告警并降级启动，由具体接口返回明确错误。Neo4j 仅在健康检查时惰性连接；如不需要 Neo4j，可移除 compose 中的 `neo4j` 服务及 backend 的对应 `depends_on`，业务链路不受影响。

## 五、真实数据链路

### 5.1 地图/节点/属性/笔记

```
React 页面/弹窗
  → store action（createMap/addNode/addProp/saveNote…）
  → features/mindmap/api.ts
  → utils/http.ts request()
  → /api/v1/maps|nodes|props|notes
  → FastAPI router（Pydantic 校验 + get_db）
  → service（事务、业务规则）
  → repository（SQLAlchemy 2.0）
  → PostgreSQL：maps / nodes / props
  → 返回 MapOut/TreeNodeOut，store 刷新本地缓存
```

- 列表 C-1 返回 `Page{total, items}`；整树 C-5/C-6 返回 `MapOut`（含 `nodes`/`props`）。
- `props` 同时承载属性与笔记：`note_content`、`note_tags`、`note_remark`、`doc`、`doc_path`。
- 前端不再使用 `localStorage` 持久化地图数据，刷新页面后从后端重新加载。

### 5.2 Git 仓库登记与动作

```
GitPage / RepoDialog
  → features/git/api.ts → utils/http.ts → /api/v1/git/*
  → api/v1/git/router.py
  → GitRegistryService（路径校验、每仓库 asyncio.Lock、审计）
  → GitService（真实 git CLI，线程池执行）
  → GitRepository（SQL）
  → PostgreSQL：git_repos / git_actions
  → 同时读取磁盘仓库实时状态，组装 GitRepoOut 返回
```

Git 运行时状态（`branch/upstream/ahead/behind/merging/files/conflicts`）不落库；提交历史 A-11 直接由 `git log` 读取。

## 六、关键架构决策（ADR）

### ADR-001 PostgreSQL 作为事实主库

- **背景**：知识仓库登记、地图/节点/属性/笔记、动作审计需要关系型事务与约束保障。
- **决策**：PostgreSQL 17 作为唯一事实主库，通过 Alembic `0001_baseline` 建立 5 张表（`git_repos`、`git_actions`、`maps`、`nodes`、`props`），ORM 与迁移一一对应；空库可用 `backend/migrations/001_init.sql` 快速初始化。
- **后果**：主数据具备唯一约束、外键级联与部分唯一索引；地图/节点/属性/笔记与 Git 登记/审计均已接入读写。早期 10 表设计（`knowledge_repository`、`knowledge_map`、`map_node`、`node_property`、`document`、`node_document_link`、`node_link`、`operation_audit`、`git_action`、`document_embedding`）未落地，仅作历史设计参考。

### ADR-002 Neo4j 退化为可选健康检查

- **背景**：旧版本曾以 Neo4j 承载笔记/关系/图谱/聚类查询；当前新结构未迁移这些业务路由。
- **决策**：`backend/app` 不包含 Neo4j 业务读写，也不初始化索引；仅在 `/api/v1/health/neo4j` 做连通性探测。compose 保留 `neo4j` 容器，可按需移除。
- **后果**：Neo4j 不保存主数据，不参与业务链路；不存在 PostgreSQL 与 Neo4j 的同步问题。

### ADR-003 Git 能力使用服务端真实仓库 + git CLI

- **背景**：前端无法可靠访问真实仓库、冲突 stage 与远端凭证。
- **决策**：`GitService` 通过 `subprocess.run` 调用系统 `git`，参数以列表传递且 `shell=False`，设置 `timeout=settings.GIT_OPERATION_TIMEOUT`，通过 `-c user.name/-c user.email` 注入提交身份，并设置 `GIT_TERMINAL_PROMPT=0`。
- **后果**：能力与真实 Git 一致，可用临时裸远端做集成测试；部署镜像必须安装 `git`；凭证由部署环境预配置，产品不提供凭证管理 UI。

### ADR-004 知识仓库限定在 KNOWLEDGE_ROOT

- **背景**：服务端执行 Git 命令存在越权访问产品代码或系统文件的风险。
- **决策**：登记路径以 `KNOWLEDGE_ROOT` 为根解析，拒绝绝对路径、`..` 与符号链接逃逸；每次操作前重新解析并校验目录存在。
- **后果**：所有 Git 操作被限制在知识目录内；产品工程仓库与知识仓库物理隔离；`DELETE /git/repos/{id}` 只删除登记，不删除文件。

### ADR-005 前端使用 HashRouter

- **背景**：生产环境由 Nginx 托管静态产物，`nginx.conf` 虽已配置 `try_files` 兜底，但不同部署方式（本地静态服务器、对象存储等）不一定提供 SPA 回退。
- **决策**：使用 `react-router-dom` v6 的 `HashRouter`。
- **后果**：`#/`、`#/map/:mapId`、`#/git`、`#/note` 在任意静态托管方式下均可直接刷新；URL 带 `#`，不参与服务端路由。

### ADR-006 统一响应与业务异常体系

- **背景**：需要前后端稳定的错误契约。
- **决策**：成功响应统一为 `{code: 200, msg, data}`；业务异常继承 `AppException(msg, code)`（默认 400），另有 `NotFoundError(404)`、`ForbiddenError(403)`；`register_exception_handlers` 将业务异常、请求校验错误（422）、HTTP 异常与未捕获异常统一转换为 `{code, msg, data: null}`，HTTP 状态码与 `code` 一致。
- **后果**：前端 `utils/http.ts` 只按 `code === 200` 解包；校验失败返回 422，业务规则失败返回 400。

### ADR-007 每仓库 asyncio.Lock 串行化

- **背景**：并发执行 `git add/commit/merge` 会破坏索引或产生竞态。
- **决策**：Git 服务维护进程级 `_LOCKS: dict[str, asyncio.Lock]`，按仓库 UUID 取锁；Git 同步调用通过 `run_in_threadpool` 执行，避免阻塞事件循环。
- **后果**：同仓库操作串行、不同仓库可并行；锁只在单进程内有效，多 worker/多副本部署时需外部锁。

### ADR-008 Git 动作写入 git_actions 审计

- **背景**：需要追踪何时对哪个知识仓库执行了什么操作及结果。
- **决策**：Git 服务在成功和业务失败时都写入 `git_actions`；成功消息包含「冲突」时记 `ok=false`（拉取产生冲突属于未完成状态）。
- **后果**：动作记录与仓库视图一同返回（A-2 默认最近 60 条），前端无需额外请求；审计写入与业务操作在同一会话中提交。

### ADR-009 JWT 预留 + 匿名开关

- **背景**：接口契约要求预留鉴权，但当前不提供登录接口。
- **决策**：`core/security.py` 提供 OAuth2PasswordBearer、JWT 编解码与 `get_current_user`；`ALLOW_ANONYMOUS=true`（默认）时返回匿名用户并放行，关闭后要求 Bearer Token。
- **后果**：当前部署默认可匿名访问；开启鉴权需外部签发 token，产品内无登录/用户管理界面。

## 七、横切关注点

| 关注点 | 现状 |
|--------|------|
| 配置 | `app/core/config.py` 使用 `pydantic-settings`，读取 `backend/.env`，未知环境变量忽略（`extra="ignore"`） |
| 异常处理 | `app/core/exceptions.py` 注册 4 类处理器；服务层只抛 `AppException` 子类 |
| 参数校验 | Pydantic v2 + `Query(ge/le)`；`GitCommitIn`、`ConflictResolveIn` 使用 `model_validator` 做跨字段校验；失败返回 422 |
| 分页 | `app/core/pagination.py` 的 `Page{total, items}`；`page≥1`、`page_size 1–100` |
| 健康检查 | `/api/v1/health` 进程存活；`/health/postgres`、`/health/neo4j` 返回 `{connected, message}` |
| 日志与可观测性 | 标准库 `logging`，仅记录启动/降级/未处理异常；无指标、链路追踪、结构化日志与告警 |
| 跨域 | `CORSMiddleware` 的源来自 `CORS_ORIGINS`（默认 5173/8080） |
| 静态资源 | 前端由 `linkmind-web`（Nginx）托管；后端只提供 API 与 `/docs` |
| 事务 | 请求级 `AsyncSession` 由 `get_db` 注入并在异常时回滚；服务层显式 `commit()` |

## 八、安全边界

| 风险 | 防护实现 | 边界说明 |
|------|----------|----------|
| 仓库路径穿越 | `resolve_repo_path()` 拒绝绝对路径与 `..`，`resolve()` 后必须位于 `KNOWLEDGE_ROOT` 内 | 符号链接解析后同样受边界约束 |
| Git 文件路径穿越 | `GitService._safe_rel()` 拒绝空值、`-` 开头、绝对路径、`..`、`.git` 首段，并做真实路径边界校验 | 所有文件参数统一经过该校验 |
| 命令注入 | 所有 Git 命令以参数列表执行，`shell=False`；不使用字符串拼接命令 | 提交信息作为 `-m` 的独立参数传入 |
| 文件大小 | `GIT_MAX_FILE_BYTES` 默认 262144（256KB）；冲突预览与自定义合并内容均受此限制 | 仅覆盖 Git 冲突内容，不是通用上传限制 |
| 目录扫描越权 | `/fs/dirs`、`/fs/tree`、`/docs/content` 只允许 `KNOWLEDGE_ROOT` 内路径，跳过符号链接、隐藏目录与 `node_modules` 等 | 最大深度 20，单文件读取上限 256KB |
| 知识库与产品仓库隔离 | 知识仓库根目录独立挂载；产品代码仓库不注册、不执行 Git 操作 | compose 默认挂载 `../docs/示例知识库` |
| 凭证 | 由运行环境预置 SSH key / HTTPS 凭证；`GIT_TERMINAL_PROMPT=0` 禁止交互式询问 | 产品不保存、不展示凭证 |
| 认证授权 | JWT 依赖已接入，`ALLOW_ANONYMOUS` 默认 `true`；无登录接口与用户体系 | 生产环境应设置 `ALLOW_ANONYMOUS=false` 并由外部签发 token，或用网络边界保护 |

## 九、实现边界与已知缺口

以下内容与当前代码一致，文档不作能力假设：

1. **历史 10 表方案未实现**：`knowledge_repository`、`knowledge_map`、`map_node`、`node_property`、`document`、`node_document_link`、`node_link`、`operation_audit`、`git_action`、`document_embedding` 均不存在于当前迁移与 ORM；当前只有 5 张表，详见 [19_数据库设计.md](./19_数据库设计.md)。
2. **Neo4j 不承载业务**：仅有健康检查端点；无笔记/关系/图谱/聚类业务路由，也无索引初始化。
3. **仓库锁为单进程锁**：`_LOCKS` 不跨进程，多副本部署时同一仓库可能并发执行。
4. **无登录/用户/权限界面**：鉴权仅预留 JWT 与匿名开关，`git_actions` 无操作者字段。
5. **可观测性有限**：无指标、链路追踪、结构化日志与告警。
