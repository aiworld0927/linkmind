# LinkMind 运维手册

## 一、磁盘管理

### 1.1 磁盘膨胀原因分析

开发过程中虚拟机磁盘从 20GB 膨胀到 120GB 的主要原因：

| 原因 | 占比 | 说明 |
|------|------|------|
| Docker 镜像缓存 | ~60% | 多次构建和拉取镜像，旧镜像未清理 |
| Docker 容器 | ~5% | 已停止但未删除的容器占用空间 |
| Docker 本地卷 | ~10% | PostgreSQL 数据卷（`pg-data`）；Neo4j 数据卷（可选组件） |
| Node.js 依赖 | ~15% | `node_modules` 和 `.node` 目录 |
| Python 虚拟环境 | ~5% | `.venv` 目录 |
| 构建缓存 | ~3% | Vite/Webpack 构建缓存 |
| 系统日志 | ~2% | 长时间运行产生的日志 |

### 1.2 磁盘清理步骤

#### 步骤一：清理 Docker 资源（最有效）

```bash
# 查看 Docker 磁盘使用情况
docker system df

# 清理所有未使用的资源（推荐）
docker system prune -a

# 清理未使用的卷（谨慎使用，会删除数据卷）
docker volume prune

# 删除特定未使用的镜像
docker rmi <IMAGE_ID>

# 删除已停止的容器
docker rm $(docker ps -a -q)

# 删除所有悬空镜像
docker rmi $(docker images -f "dangling=true" -q)
```

#### 步骤二：清理 Node.js 依赖

```bash
# 清理前端 node_modules（重新安装时会重建）
rm -rf frontend/node_modules

# 清理 npm 缓存
npm cache clean --force

# 清理 .node 目录（如果不再需要）
rm -rf .node
```

#### 步骤三：清理 Python 虚拟环境

```bash
# 清理后端虚拟环境（重新安装时会重建）
rm -rf backend/.venv
```

#### 步骤四：清理构建缓存

```bash
# 清理 Vite 构建缓存
rm -rf frontend/.vite

# 清理前端构建产物（开发环境不需要）
rm -rf frontend/dist
```

#### 步骤五：清理系统日志

```bash
# 清理系统日志
sudo journalctl --vacuum-size=100M

# 清理 apt 缓存
sudo apt clean

# 清理旧内核（谨慎使用）
sudo apt autoremove --purge
```

### 1.3 VMware 虚拟机磁盘压缩

#### 方法一：在虚拟机内清理后压缩（推荐）

1. **在虚拟机内执行清理**（见上文步骤）
2. **填充空闲空间为零**：
   ```bash
   sudo dd if=/dev/zero of=/tmp/zeros bs=1M
   sudo rm /tmp/zeros
   ```
3. **关闭虚拟机**
4. **在 VMware Workstation 中压缩**：
   - 选择虚拟机 → 右键 → 管理 → 清理磁盘
   - 或使用命令行：
     ```bash
     vmware-vdiskmanager -k "/path/to/your/virtual_machine.vmdk"
     ```

#### 方法二：使用 VMware 压缩工具

```bash
# Windows
"C:\Program Files (x86)\VMware\VMware Workstation\vmware-vdiskmanager.exe" -k "D:\VMs\linkmind.vmdk"

# Linux
vmware-vdiskmanager -k "/var/lib/libvirt/images/linkmind.qcow2"

# macOS
/Applications/VMware\ Fusion.app/Contents/Library/vmware-vdiskmanager -k "/Users/username/Documents/Virtual Machines/linkmind.vmdk"
```

### 2.3 备份策略

#### PostgreSQL 主库备份（必需）

PostgreSQL 是事实主库，保存 `git_repos` / `git_actions` / `maps` / `nodes` / `props` 5 张业务表，必须纳入备份。

```bash
# 创建备份目录
mkdir -p /backup/postgres

# 逻辑备份（自定义格式，支持并行恢复与选择性恢复）
docker exec linkmind-postgres pg_dump \
  -U "${POSTGRES_USER:-linkmind}" \
  -d "${POSTGRES_DB:-linkmind}" \
  -Fc -f /tmp/linkmind-$(date +%Y%m%d-%H%M).dump

# 拷贝到宿主机
docker cp linkmind-postgres:/tmp/linkmind-$(date +%Y%m%d-%H%M).dump /backup/postgres/
```

也可在宿主机直接执行（需安装 PostgreSQL 客户端）：

```bash
pg_dump -h localhost -p 5432 -U linkmind -Fc -f /backup/postgres/linkmind-$(date +%Y%m%d-%H%M).dump linkmind
```

#### 自动备份脚本

脚本已随仓库提供：[scripts/backup.sh](../scripts/backup.sh)（内容如下，可按环境调整备份目录）：

```bash
#!/bin/bash
set -euo pipefail

BACKUP_DIR="/backup/postgres/$(date +%Y%m%d)"
mkdir -p "$BACKUP_DIR"
FILE="$BACKUP_DIR/linkmind-$(date +%Y%m%d-%H%M).dump"

echo "=== 开始备份 PostgreSQL 主库 ==="
docker exec linkmind-postgres pg_dump \
  -U "${POSTGRES_USER:-linkmind}" \
  -d "${POSTGRES_DB:-linkmind}" \
  -Fc -f "/tmp/$(basename "$FILE")"
docker cp "linkmind-postgres:/tmp/$(basename "$FILE")" "$FILE"

# 清理 7 天前的备份
find /backup/postgres -type d -mtime +7 -exec rm -rf {} +

echo "=== 备份完成: $FILE ==="
```

配置定时任务：

```bash
crontab -e

# 添加每日凌晨2点备份
0 2 * * * bash /coding/linkmind/scripts/backup.sh >> /var/log/linkmind_backup.log 2>&1
```

#### Neo4j 数据备份（可选组件）

Neo4j 仅用于健康检查连通性验证，不保存主数据；若部署了 Neo4j 且需要保留其派生数据，可按以下方式备份：

```bash
mkdir -p /backup/neo4j
docker compose -f deploy/docker-compose.yml stop neo4j
docker run --rm \
  -v deploy_neo4j-data:/data \
  -v /backup/neo4j:/backup \
  neo4j:5.26.0 \
  neo4j-admin database backup --to-path=/backup neo4j
docker compose -f deploy/docker-compose.yml start neo4j
```

> 卷名以 `docker volume ls` 实际输出为准（compose 项目名前缀可能不同）。

### 2.6 Docker Compose 与 deploy/.env 注意事项

- 统一使用 `deploy/docker-compose.yml`，并以 `deploy/.env` 作为环境变量来源：

  ```bash
  cp deploy/.env.example deploy/.env      # 首次部署
  docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build
  ```

- **POSTGRES_* 环境变量污染**：宿主机 shell 中若已存在 `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` / `POSTGRES_PORT`，会覆盖 compose 的默认值，导致容器与后端 `DATABASE_URL` 指向不一致。部署时务必在 `deploy/.env` 中显式声明，并在启动前检查：

  ```bash
  grep -E '^POSTGRES_' deploy/.env
  docker compose --env-file deploy/.env -f deploy/docker-compose.yml config | grep -A5 postgres
  ```

- **初始化 SQL 仅空卷执行**：`backend/migrations/001_init.sql` 挂载到 `/docker-entrypoint-initdb.d/`，只在 `pg-data` 卷为空时执行一次（脚本会写入 `alembic_version = '0001_baseline'`，与 Alembic 状态对齐）。已有数据卷不会重复执行；结构变更请使用 Alembic：

  ```bash
  cd backend && .venv/bin/python -m alembic upgrade head
  ```

- `SECRET_KEY` 生产必须替换为 ≥32 字节随机值；`CORS_ORIGINS` 填写真实前端源，禁止与 `allow_credentials=true` 搭配 `*`。
- 容器内不读取 `backend/.env`，JWT / CORS / `DATABASE_URL` 等必须由 compose 注入。

## 三、故障排查

### 3.1 常见问题

#### Q1: 服务无法启动

**原因**：端口被占用、配置错误、依赖缺失、数据库未就绪

**解决方案**：

```bash
# 检查端口占用
lsof -i :8000

# 检查配置文件
cat backend/.env

# 检查 Docker 日志
docker compose -f deploy/docker-compose.yml logs linkmind-backend

# 检查 PostgreSQL 连通性
docker exec linkmind-postgres pg_isready -U "${POSTGRES_USER:-linkmind}" -d "${POSTGRES_DB:-linkmind}"
```

> 后端启动时会探测 PostgreSQL，连接失败会降级启动（接口返回明确错误），因此“进程在跑但业务 500”通常应优先检查 `DATABASE_URL`。

#### Q2: 数据库连接失败

**原因**：PostgreSQL 未启动、`DATABASE_URL` 配置错误、账号/库不存在、网络或端口问题

**解决方案**：

```bash
# 检查 PostgreSQL 容器状态
docker compose -f deploy/docker-compose.yml ps postgres

# 重启 PostgreSQL
docker compose -f deploy/docker-compose.yml restart postgres

# 查看容器日志
docker compose -f deploy/docker-compose.yml logs --tail=100 postgres

# 校验连接（示例）
psql "postgresql://linkmind:linkmind@localhost:5432/linkmind" -c "SELECT 1;"

# 检查后端实际使用的连接串
docker exec linkmind-backend env | grep DATABASE_URL
```

> 容器内主机名应为 `postgres`（`postgresql+asyncpg://<user>:<pass>@postgres:5432/<db>`），宿主机直连才用 `localhost`。

#### Q3: 前端页面无法访问

**原因**：前端服务未启动、端口配置错误、API 代理/基础地址问题

**解决方案**：

```bash
# 开发环境检查 Vite 服务（5173）
curl http://localhost:5173

# 生产环境检查 nginx 服务（8080）
curl http://localhost:8080

# 检查代理配置与 API 基础地址
cat frontend/vite.config.ts
cat frontend/.env.development   # VITE_API_BASE_URL

# 重启前端开发服务
cd frontend && npm run dev

# 重启生产前端容器
docker compose -f deploy/docker-compose.yml restart linkmind-web
```

#### Q4: 内存/连接数不足

**原因**：后端容器内存限制、PostgreSQL 连接池耗尽、查询过于复杂

**解决方案**：

```bash
# 查看容器资源占用
docker stats

# 调整后端连接池（deploy/.env）
DB_POOL_SIZE=10
DB_MAX_OVERFLOW=20

# 查看 PostgreSQL 连接占用
docker exec linkmind-postgres psql -U "${POSTGRES_USER:-linkmind}" -d "${POSTGRES_DB:-linkmind}" \
  -c "SELECT state, count(*) FROM pg_stat_activity GROUP BY state;"

# 如部署了 Neo4j（可选），调整其内存
NEO4J_dbms_memory_heap_max__size=4G
NEO4J_dbms_memory_pagecache_size=2G
```

### 3.2 紧急恢复

```bash
# 停止应用写入（保留数据库）
docker compose -f deploy/docker-compose.yml stop linkmind-backend linkmind-web

# 恢复 PostgreSQL 主库（先确认目标库为空或已备份）
docker cp /backup/postgres/latest/linkmind.dump linkmind-postgres:/tmp/restore.dump
docker exec linkmind-postgres pg_restore \
  -U "${POSTGRES_USER:-linkmind}" \
  -d "${POSTGRES_DB:-linkmind}" \
  --clean --if-exists /tmp/restore.dump

# 启动服务
docker compose -f deploy/docker-compose.yml up -d

# 验证恢复
curl http://localhost:8000/api/v1/health
curl http://localhost:8000/api/v1/health/postgres
curl http://localhost:8000/api/v1/maps
```

## 五、版本更新

### 5.1 更新流程

1. **备份数据**（见第二章）
2. **拉取最新代码**：
   ```bash
   git pull origin main
   ```
3. **更新依赖**：
   ```bash
   cd backend && uv pip install -e .
   cd frontend && npm install
   ```
4. **构建前端**：
   ```bash
   cd frontend && npm run build
   ```
5. **重启服务**：
   ```bash
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml down
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build
   ```
6. **验证服务**：
   ```bash
   curl http://localhost:8000/api/v1/health
   curl http://localhost:8000/api/v1/health/postgres
   ```

### 5.2 回滚流程

```bash
# 回滚代码
git log --oneline -5
git checkout <COMMIT_HASH>

# 重启服务
docker compose --env-file deploy/.env -f deploy/docker-compose.yml down
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build

# 数据库回滚（如本次发布包含迁移，先确认已备份）
cd backend && .venv/bin/python -m alembic downgrade -1

# 验证回滚
curl http://localhost:8000/api/v1/health
```

## 七、合规性检查

### 7.1 安全检查清单

- [ ] 防火墙仅开放必要端口（80, 443, 8000, 5432；Neo4j 7687/7474 仅在部署可选组件时开放）
