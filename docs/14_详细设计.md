## 二、Git 状态机与 porcelain 码映射

### 2.1 状态采集

`GitService.status()` 执行：

```bash
git status --porcelain=v1 -z --branch
```

- 以 `\0` 切分；`## ` 开头为分支行，交给 `_parse_branch()`。
- 分支行解析 `branch...upstream [ahead N, behind M]`；兼容 `No commits yet on <branch>` 与 `HEAD (no branch)`；无上游时 `upstream=None`。
- 文件记录格式为 `XY path`；当 `X` 或 `Y` 含 `R`/`C` 时，`-z` 模式后续还有一个原路径 token，需跳过。
- `merging` 通过 `.git/MERGE_HEAD` 是否存在判断，不依赖分支行。

### 2.2 文件状态映射（`_map_state`）

| porcelain 码 | `state` | 说明 | `conflict` | `staged` |
|--------------|---------|------|------------|----------|
| `??` | `untracked` | 未跟踪 | false | false |
| `DD` | `conflict` | 双方都删除 | true | false |
| `AU` | `conflict` | 本地新增、远端未合并 | true | false |
| `UD` | `conflict` | 本地修改、远端删除 | true | false |
| `UA` | `conflict` | 远端新增、本地未合并 | true | false |
| `DU` | `conflict` | 本地删除、远端修改 | true | false |
| `AA` | `conflict` | 双方都新增 | true | false |
| `UU` | `conflict` | 双方都修改 | true | false |
| 含 `R` | `renamed` | 重命名 | false | 首字符非空格/`?` 时为 true |
| 含 `C` | `copied` | 复制 | false | 同上 |
| 含 `A` | `added` | 新增 | false | 同上 |
| 含 `D` | `deleted` | 删除 | false | 同上 |
| 含 `M` 或 `T` | `modified` | 修改/类型变化 | false | 同上 |
| 其他 | `changed` | 兜底 | false | 同上 |

> 判断顺序固定为 `??` → 冲突码 → `R` → `C` → `A` → `D` → `M/T` → `changed`；冲突码优先于其他字符判断。

### 2.3 冲突生命周期

```
正常状态
  │ git merge（pull）返回非 0 且存在冲突
  ▼
merging=true（存在 .git/MERGE_HEAD）
  ├─ 冲突文件 code ∈ {DD,AU,UD,UA,DU,AA,UU}
  ├─ resolve_conflict(path, ours|theirs|content)
  │    ├─ ours  → stage 2 存在：git checkout --ours -- path；不存在：git rm -f -- path
  │    ├─ theirs→ stage 3 存在：git checkout --theirs -- path；不存在：git rm -f -- path
  │    └─ content → 校验 ≤256KB，写入工作区，git add -- path
  │  （每次解决后自动 git add，冲突数减少）
  ├─ 仍有冲突 → continue_merge 拒绝（409）
  └─ 全部解决 → continue_merge：git commit --no-edit → merging=false
       或 abort_merge：git merge --abort → 恢复合并前状态
```

`resolve_conflict()` 会先确认路径属于当前 `status().conflicts`，否则返回 400「不是当前冲突文件」。`continue_merge()` 与 `abort_merge()` 都要求 `MERGE_HEAD` 存在，否则 400。

### 2.4 状态转移（操作结果）

| 起始状态 | 操作 | 成功结果 | 失败结果 |
|----------|------|----------|----------|
| clean / dirty | commit | 生成提交，文件状态清空 | 冲突 → 409；无暂存 → 400；路径非法 → 400 |
| 有上游、落后 | pull | 快进或合并成功 | 无上游 400；合并冲突返回成功消息并保持 `merging=true`；其他 Git 错误 400 |
| 有未推送提交 | push | 远端更新 | 无上游 400；非快进/被拒 409；其他 400 |
| merging + 冲突 | resolve | 冲突文件减少 | 路径非冲突 400；内容超限 400 |
| merging + 无冲突 | continue | 合并提交，`merging=false` | 仍有冲突 409；无 MERGE_HEAD 400 |
| merging | abort | 回到合并前，`merging=false` | 无 MERGE_HEAD 400 |

## 三、Git API 契约

### 3.1 通用约定

- 前缀 `/api/v1`，JSON 请求/响应。
- 成功：HTTP 200 + `{code: 200, msg: string, data: object}`。
- 失败：Git 路由经 `exception_handler` 返回与 `code` 一致的 HTTP 状态码；部分既有 Neo4j 路由仍以 HTTP 200 返回 `code=500` 的 `error_response`（遗留行为，不在 Git 契约内）。
- `repo_id` 为 UUID；Pydantic 校验失败由 `RequestValidationError` 转为 400，`msg` 取第一条错误信息。

### 3.2 端点详表

| 方法/路径 | 请求 | 校验 | 成功 `data` | 主要错误 |
|-----------|------|------|-------------|----------|
| `GET /git/repos` | 无 | 无 | `{repos: GitRepoView[]}` | PostgreSQL 不可用 → 500 |
| `POST /git/repos` | `GitRepoCreateRequest` | `name` 1–120；`fs_path` ≤1024，默认空；`init` bool；`remote_url` ≤1024 | `GitRepoView`，`msg="仓库登记成功"` | 名称重复 409；目录已登记 409；目录不存在 404；不是目录 400；不是 Git 仓库且未 init 400；路径越界 400 |
| `GET /git/repos/{repo_id}` | 路径 UUID | 仓库必须存在 | `GitRepoView` | 404 知识仓库不存在 |
| `DELETE /git/repos/{repo_id}` | 路径 UUID | 仓库必须存在 | `{removed: true}`，`msg="已移除仓库登记"` | 404 |
| `POST /git/repos/{repo_id}/commit` | `GitCommitRequest` | `message` 1–500；必须 `all=true` 或 `paths` 非空 | `GitRepoView`，`msg` 为「提交完成」 | 冲突 409；无变更 400；路径非法 400；超时 408 |
| `POST /git/repos/{repo_id}/pull` | 无 body | 必须配置上游 | `GitRepoView`，`msg` 为「拉取完成 / 已是最新版本 / 拉取产生冲突，请解决后完成合并」 | 无上游 400；其他 400；超时 408 |
| `POST /git/repos/{repo_id}/push` | 无 body | 必须配置上游 | `GitRepoView`，`msg="推送完成"` | 无上游 400；非快进/被拒 409；其他 400 |
| `POST /git/repos/{repo_id}/conflicts/resolve` | `GitResolveRequest` | `path` 非空；`strategy ∈ {ours,theirs,content}`；`strategy=content` 时 `content` 必须非 null；内容 ≤256KB | `GitRepoView`，`msg` 为「已保留本地版本 / 已保留远端版本 / 已保存合并结果」 | 非冲突文件 400；缺内容 400；超限 400 |
| `POST /git/repos/{repo_id}/merge/continue` | 无 body | 必须存在 `MERGE_HEAD` 且无冲突 | `GitRepoView`，`msg="合并完成"` | 无合并 400；仍有冲突 409 |
| `POST /git/repos/{repo_id}/merge/abort` | 无 body | 必须存在 `MERGE_HEAD` | `GitRepoView`，`msg="已放弃合并"` | 无合并 400 |
| `GET /git/repos/{repo_id}/log` | Query `limit` | `1 ≤ limit ≤ 100`，默认 20 | `{log: GitCommit[]}` | 404；非法 limit 400 |
| `GET /git/repos/{repo_id}/actions` | Query `limit` | `1 ≤ limit ≤ 200`，默认 60 | `{actions: GitActionView[]}` | 404；非法 limit 400 |

> 说明：`log` 端点接受 `limit=1..100`，但仓库视图组装时只读取最近 20 条，因此实际最多返回 20 条；`actions` 端点接受 `limit=1..200`，视图只组装最近 60 条，因此实际最多返回 60 条。

### 3.3 响应模型

```text
GitRepoView:
  id, name, path, fs_path, branch, upstream, ahead, behind, remote,
  merging, files: GitFile[], conflicts: GitConflict[], counts: GitCounts,
  log: GitCommit[], actions: GitActionView[]

GitFile:        path, code, state, staged, conflict
GitConflict:    path, ours, theirs, working
GitCommit:      hash, short_hash, author, date, subject
GitActionView:  id, ts, action, message, files, ok
GitCounts:      total, staged, unstaged, untracked, conflict
```

`counts` 计算顺序：`total` 为全部文件；冲突计入 `conflict`；`untracked` 单独计数；其余按 `staged` 是否为 true 分入 `staged` 或 `unstaged`。

### 3.4 错误码语义

| 异常/场景 | HTTP `code` | `msg` 示例 |
|-----------|-------------|------------|
| `BusinessError` 默认 | 400 | 业务校验失败 |
| `GitError(400, ...)` | 400 | Git 命令失败最后一行；路径越界；无上游；无变更；内容超限 |
| `GitError(404, ...)` | 404 | 目录不存在 |
| `GitError(408, ...)` | 408 | `Git 操作超时（>60s）` |
| `GitError(500, ...)` | 500 | `服务器未安装 git` |
| `NotFoundError` | 404 | `知识仓库不存在`；`知识仓库目录不存在，请检查挂载路径` |
| `ConflictError` | 409 | `仓库名称已存在`；`该目录已登记为知识仓库`；`存在未解决的冲突，请先解决后再提交`；`远端有新提交，请先拉取`；`仍有未解决的冲突` |
| Pydantic 校验失败 | 400 | 第一条校验错误信息（如「请选择要提交的文件，或勾选提交全部变更」） |
| 未捕获异常 | 500 | `str(exc)`，并打印 traceback |

## 四、数据库设计

### 4.1 表设计与索引

| 表 | 用途 | 主键 / 外键级联 | 关键字段 | 约束与索引 | 优化理由 |
|----|------|-----------------|----------|------------|----------|
| `knowledge_repository` | 知识仓库登记 | PK `id`；被 `knowledge_map`（SET NULL）和 `git_action`（CASCADE）引用 | `name`、`fs_path`、`git_remote`、`default_branch`、`last_synced_at` | `name` UNIQUE、`fs_path` UNIQUE | 名称/路径查重为登记高频路径，唯一约束兼作索引 |
| `knowledge_map` | 知识地图 | PK `id`；`repository_id` → `knowledge_repository` ON DELETE SET NULL | `title`、`description`、`source_path`、`git_status` | `uq_knowledge_map_repo_title(repository_id,title)`；`ix_knowledge_map_repository` | 同一仓库下标题唯一；按仓库列地图 |
| `map_node` | 地图节点（父子层级） | PK `id`；`map_id` → `knowledge_map` CASCADE；`parent_id` → `map_node` CASCADE | `name`、`path`、`depth`、`sort_order`、`is_expanded`、`display_mode` | `ck_map_node_display_mode`；`ix_map_node_tree(map_id,depth,sort_order)`；`ux_map_node_root_name(map_id,name) WHERE parent_id IS NULL`；`ux_map_node_child_name(parent_id,name) WHERE parent_id IS NOT NULL` | 部分唯一索引分别保证同层根节点/子节点重名；树索引服务层级查询与排序 |
| `node_property` | 节点属性（笔记） | PK `id`；`node_id` → `map_node` CASCADE | `label`、`content`、`tags text[]`、`remark`、`document_path`、`sort_order` | `ix_node_property_node(node_id,sort_order)`；GIN `ix_node_property_tags(tags)`；GIN `ix_node_property_search(to_tsvector('simple', label||' '||content))` | 按节点取笔记；标签数组包含查询；简单全文检索 |
| `document` | 知识仓库内文档 | PK `id`；`repository_id` → `knowledge_repository` CASCADE | `relative_path`、`title`、`content`、`checksum`、`git_status` | `uq_document_repo_path(repository_id,relative_path)`；`ix_document_repo_status(repository_id,git_status)`；GIN `ix_document_search(to_tsvector('simple', coalesce(title,'')||' '||content))` | 文档路径唯一；按仓库+状态筛变更；标题/正文检索 |
| `node_document_link` | 节点-文档多对多 | PK `(node_id,document_id)`；两侧 CASCADE | `created_at` | 复合主键 | 天然去重，双向级联清理 |
| `node_link` | 节点依赖关系 | PK `(source_node_id,target_node_id)`；两侧 CASCADE | `created_at` | `ck_node_link_not_self`；`ix_node_link_target(target_node_id)` | 禁止自依赖；反向查询目标节点 |
| `operation_audit` | 地图/节点操作审计 | PK `id bigserial`；`map_id` → `knowledge_map` SET NULL | `actor`、`action`、`target_type`、`target_id`、`summary`、`payload jsonb` | `ix_operation_audit_map_time(map_id,created_at DESC)`；BRIN `ix_operation_audit_time_brin(created_at)` | 按地图倒序查最近操作；BRIN 适合只追加的大表时间范围扫描 |
| `git_action` | Git 动作审计 | PK `id bigserial`；`repository_id` → `knowledge_repository` CASCADE | `action`、`message`、`files jsonb`、`ok`、`detail` | `ix_git_action_repo_time(repository_id,created_at DESC)` | 仓库视图每次读取最近 60 条 |
| `document_embedding` | 文档向量 | PK/FK `document_id` → `document` CASCADE | `model`、`embedding vector(1536)`、`updated_at` | ivfflat `ix_document_embedding_vector(embedding vector_cosine_ops) WITH (lists=100)` | 1536 维余弦相似检索；ivfflat 以少量召回换取近似最近邻性能 |

### 4.2 索引类型分布

| 类型 | 索引 | 作用 |
|------|------|------|
| B-tree | `ix_knowledge_map_repository`、`ix_map_node_tree`、`ix_node_property_node`、`ix_document_repo_status`、`ix_node_link_target`、`ix_operation_audit_map_time`、`ix_git_action_repo_time` | 等值/范围/排序 |
| 部分唯一 B-tree | `ux_map_node_root_name`、`ux_map_node_child_name` | 仅对根/子节点分别去重 |
| GIN | `ix_node_property_tags`、`ix_node_property_search`、`ix_document_search` | 数组包含、全文检索 |
| BRIN | `ix_operation_audit_time_brin` | 时间追加型大表的轻量范围索引 |
| ivfflat | `ix_document_embedding_vector` | 向量近似最近邻 |

DDL 使用 `CREATE EXTENSION IF NOT EXISTS vector`、`CREATE TABLE IF NOT EXISTS`、`CREATE INDEX IF NOT EXISTS`，可重复执行。ORM 中 `map_node` 的两个部分唯一索引用 `Index(..., unique=True, postgresql_where=...)` 表达，与 SQL 名称一致。

### 4.3 数据访问层规范

1. **路由不写 SQL**：路由只做依赖注入、调用服务、`success_response`。
2. **仓储只接收 `AsyncSession`**：`BaseRepository.__init__(session)`；仓储不创建会话、不关闭会话。
3. **事务边界在服务层**：服务在完成一组写入后显式 `await session.commit()`；异常由 `get_session()` 统一回滚。
4. **flush/refresh 约定**：仓储写入后 `flush()` 以取得自增 ID 或触发约束；需要读取数据库默认值时再 `refresh()`。当前 `git_repository.create()` 与 `add_action()` 均使用 `flush()`。
5. **会话配置**：`async_sessionmaker(expire_on_commit=False, autoflush=False)`，避免提交后属性过期与隐式刷新。
6. **连接池**：`pool_pre_ping=True`、`pool_size=DB_POOL_SIZE`、`max_overflow=DB_MAX_OVERFLOW`。
7. **模型与 DDL 同步**：任何表/索引变更需同时更新 `models/db_models.py` 与 `migrations/001_init.sql`。

- 工作区干净：表格 `emptyText="工作区干净，没有待提交的变更"`。

- 动作记录为空：`Empty`「暂无动作记录」。

## 六、笔记 Markdown 渲染范围与安全策略

### 6.1 渲染链路

```
NoteList「查看」
  → buildNoteMarkdown(item,title)  # # 标题 / 正文 / 标签 / 创建时间
  → navigate('/note?title=&node=&md=')
  → NotePage 读取 searchParams
  → renderMarkdown(md) → { html, headings }
  → MarkdownView：dangerouslySetInnerHTML 渲染 html + 大纲/滚动高亮
```

### 6.2 支持范围

`features/notes/markdown.ts` 仅支持笔记场景子集：

| 语法 | 输出 | 说明 |
|------|------|------|
| `#` / `##` / `###` | `<h1..h3 id="h-N">` | 按出现顺序编号，收集 `headings` |
| `-` `*` `+` 开头 | `<ul><li>` | 连续项合并；类型切换自动闭合 |
| `1.` 开头 | `<ol><li>` | 同上 |
| `>` | `<blockquote>` | 单行引用 |
| 三连 `---` 或 `***` | `<hr>` | 分隔线 |
| 围栏 ```` ``` ```` | `<pre><code>` | 代码内容整体转义；未闭合时结尾补齐 |
| 行内 `` ` `` / `**` / `*` / `[text](url)` | `code/strong/em/a` | 链接带 `target="_blank" rel="noopener"` |
| 其他非空行 | `<p>` | 空行仅关闭列表，不生成段落 |

### 6.3 安全策略

1. **先转义**：`escapeHtml()` 转义 `& < > " '`；所有文本（标题、段落、引用、代码块、链接文字）先经过转义，再替换白名单标记。
2. **不解析原始 HTML**：用户输入的 `<script>`、`<img onerror=...>` 等会变成实体文本；测试用例已覆盖。
3. **代码块**：内容整体 `escapeHtml`，不执行语法高亮注入。
4. **链接**：渲染函数允许任意 `href` 文本，但输入先转义，无法引入未转义的引号；前端未额外校验协议。若后续开放不可信内容源，需增加 `http/https/#` 协议白名单，拒绝 `javascript:`、`data:`。
5. **标题锚点**：使用 `h-<序号>` 而非用户文本，避免属性注入与重复 id。
6. **渲染出口**：仅在 `MarkdownView` 中调用 `dangerouslySetInnerHTML`，输入必须是 `renderMarkdown()` 的输出。

### 6.4 Vditor 在线编辑器（Typora 体验）

编辑态使用 Vditor 3.10，`mode: 'ir'`（即时渲染），组件为 `frontend/src/features/notes/VditorEditor.tsx`。

| 约定 | 说明 |
|------|------|
| 资源本地化 | `cdn: '/vditor'`，必要资源已随仓库放在 `frontend/public/vditor/dist/`（`js/lute/lute.min.js`、`js/i18n/zh_CN.js`、`js/icons/ant.js`、`js/highlight.js/`、`index.css`），不依赖 unpkg，离线可用；`npm run build` 会复制到 `dist/vditor`。**缺少 `js/highlight.js/` 会导致 Vite 回退返回 index.html，控制台报 `Unexpected token '<'` 与 `hljs is not defined`，代码块渲染异常（内容重复显示）** |
| 工具栏图标 | Vditor 通过 `js/icons/ant.js` 向 `document.body` 注入 `vditor-icon-*` 的 SVG symbol，缺该文件会导致工具栏按钮全部空白 |
| 编辑区宽度 | 正文版心统一为 860px：预览态由 `.lm-note-markdown` 控制，编辑态 `.lm-note-body.is-edit` 居中 960px（860 + 左右各 50px 留白）；两种模式正文宽度一致 |
| 进入方式 | 属性抽屉的「打开笔记 →」默认进入**预览模式**，页内「切换编辑」再进入 Vditor |
| 代码块 | `code` 强制 `white-space: pre`（Vditor 行内 code 规则 specificity 更高，会把代码块设成 pre-wrap 导致折行）；不要在 `after` 中直接改 `<code>` 的文本节点，会破坏 IR 模式 DOM 与数据的映射，导致编辑态内容重复显示 |
| 只初始化一次 | effect 依赖为空；`initialValue` 变化只用 `setValue()` 同步，不重建实例 |
| StrictMode 安全 | 卸载时 `destroy()` 并清空容器 `innerHTML`，避免 React 18 开发模式二次挂载时残留 DOM 报错 |
| 内容回写 | 保存时 `getValue()` → `parseNoteMarkdown()` 还原为 `note.c / note.t / note.r`，再写回 store |
| 入口 | 脑图右侧属性抽屉每个属性只有一个「打开笔记 →」入口，默认进入编辑态，页内可「切换预览」 |

## 九、脑图画布：缩放比例与拖拽平移

画布实现位于 `frontend/src/features/mindmap/MindCanvas.tsx`，布局与缩放算法位于 `frontend/src/utils/layout.ts`，均与原型 `docs/原型界面/demo-mindmap.html` 保持一致。

### 9.1 缩放常量（改这里即可调整比例）

所有比例参数集中在 [layout.ts](file:///coding/linkmind/frontend/src/utils/layout.ts) 顶部：

| 常量 | 默认值 | 含义 | 原型对应 |
|------|--------|------|----------|
| `FIT_PADDING` | `40` | 自动适配时画布四周留白（px） | `pad = 40` |
| `FIT_MIN_K` | `0.12` | 自动适配最小缩放，防止大树过小 | `Math.max(0.12, …)` |
| `FIT_MAX_K` | `1.05` | 自动适配最大缩放，防止小树过大 | `Math.min(k, 1.05)` |
| `VIEW_MIN_K` | `0.1` | 手动缩放（滚轮/按钮）下限 | `Math.max(0.1, …)` |
| `VIEW_MAX_K` | `2.6` | 手动缩放（滚轮/按钮）上限 | `Math.min(2.6, …)` |

### 9.2 进入脑图时的初始比例（fit 公式）

```ts
k = min((W - FIT_PADDING*2) / bounds.w, (H - FIT_PADDING*2) / bounds.h)
k = clamp(k, FIT_MIN_K, FIT_MAX_K)
x = (W - bounds.w*k)/2 - bounds.x*k
y = (H - bounds.h*k)/2 - bounds.y*k
```

- `W/H` 为 `#stage` 的实际像素宽高，`bounds` 为整棵树的包围盒。
- 效果：小树最多放大到 `1.05` 倍（与原型一致，不会撑满屏幕），大树自动缩小到刚好放下，且始终居中。
- **调整整体观感**：想更大/更小，改 `FIT_MAX_K`（例如 `1.2` 略大、`0.9` 略小）；想留白更多，改 `FIT_PADDING`。
- **调整手动缩放上限**：改 `VIEW_MAX_K`（当前 2.6 倍，与原型 `zoom()` 一致）。

### 9.3 拖拽平移与缩放交互

| 操作 | 行为 | 说明 |
|------|------|------|
| 按住左键拖动 | 平移整张脑图 | 画布空白处与节点上均可抓取，与原型一致；移动距离小于 4px 视为点击，不触发平移，也不会误触节点展开/收起 |
| 滚轮 | 以光标为中心缩放 | 缩放范围 `VIEW_MIN_K` ~ `VIEW_MAX_K` |
| 点击节点 | 选中并在右侧抽屉显示属性 | 有子节点时同时展开/收起 |
| 右键节点 | 打开上下文菜单 | 新增子节点 / 修改 / 删除 / 属性 |
| 点击折叠圆点 | 只展开/收起该节点 | 不改变选中项 |

实现要点：拖拽状态保存在 `useRef` 中，`mousedown` / `mousemove` / `mouseup` / `wheel` 监听器只在挂载时绑定一次（不随 `view` 变化重建），否则拖动过程中 effect 重建会丢失拖拽状态，表现为「拖一下就停」。
