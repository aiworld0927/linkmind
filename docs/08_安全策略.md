# LinkMind 安全策略

## 一、概述

本文档定义 LinkMind 知识图谱系统的安全策略，包括数据安全、应用安全、网络安全等方面的规范和要求。

## 二、安全目标

| 目标 | 说明 |
|------|------|
| 数据保密性 | 确保敏感数据不被未授权访问 |
| 数据完整性 | 确保数据在传输和存储过程中不被篡改 |
| 系统可用性 | 确保系统服务持续可用 |
| 合规性 | 符合相关法律法规和行业标准 |

## 三、数据安全

### 3.1 数据分类

| 分类 | 说明 | 示例 |
|------|------|------|
| 公开数据 | 可公开访问的数据 | 系统配置信息 |
| 内部数据 | 仅限内部人员访问 | 用户知识节点数据 |
| 敏感数据 | 需要严格保护的数据 | 用户认证信息 |

### 3.2 数据存储安全

#### 3.2.1 数据库安全

LinkMind 以 **PostgreSQL 17** 为唯一主库（`git_repos` / `git_actions` / `maps` / `nodes` / `props` 5 张业务表），安全要求：

- 通过 `DATABASE_URL`（`postgresql+asyncpg://...`）连接，账号密码置于环境变量，禁止硬编码
- 使用最小权限账号：业务账号仅授予业务表 DML 权限，禁止超级用户
- 数据库不对公网暴露，仅允许应用容器/内网访问；按需启用 SSL
- 开启连接与慢查询审计（`pg_stat_activity`、日志轮转）
- 定期更新数据库密码（同步修改 `deploy/.env` 的 `POSTGRES_PASSWORD` 与 `DATABASE_URL`）

> Neo4j 为**可选组件**，仅用于健康检查连通性验证，不保存主数据；如部署，需修改默认口令并限制端口访问。

#### 3.2.2 前端数据安全

- 业务数据（地图/节点/属性/笔记）全部通过 API 持久化到服务端 PostgreSQL
- `localStorage` 不再承载业务数据，仅保留选中、折叠、弹窗等瞬时 UI 状态
- 敏感数据不存储在前端，不写入 URL 参数
- 前端渲染默认依赖 React 转义，避免直接使用 `dangerouslySetInnerHTML`

### 3.3 数据传输安全

- 生产环境强制使用 HTTPS
- API 接口使用 TLS 1.2+ 加密
- 避免在 URL 参数中传递敏感数据
- 使用 POST 请求传输敏感信息

### 3.4 数据备份与恢复

- 定期对 PostgreSQL 主库做逻辑备份（`pg_dump -Fc`，每日增量/每周全量），并定期演练恢复
- 备份文件加密存储、存放于安全位置
- 备份范围覆盖 5 张业务表与 `alembic_version`，恢复后执行 `alembic check` 校验

## 四、应用安全

### 4.1 输入验证

#### 4.1.1 前端验证

- 使用表单验证库进行客户端验证
- 限制输入长度和格式
- 使用 React 内置转义防止 XSS
- Token 通过 `Authorization: Bearer` 请求头传递；如改为 Cookie 承载，需补充 CSRF 防护

#### 4.1.2 后端验证

- 对所有输入参数进行服务端验证
- 使用 Pydantic 模型进行数据校验
- 过滤特殊字符和恶意输入
- 限制请求大小和频率

### 4.2 路径穿越与命令执行防护

- 文件系统（`fs`）、文档（`docs`）、Git（`git`）操作全部限制在 `KNOWLEDGE_ROOT` 内，拒绝绝对路径、`..` 与符号链接逃逸，越界返回 403
- Git 子进程使用 `subprocess.run(..., shell=False)` 的参数列表形式，禁止拼接 shell 字符串
- Git 操作设置超时（`GIT_OPERATION_TIMEOUT`）与单文件大小上限（`GIT_MAX_FILE_BYTES`），防止资源耗尽
- 所有 SQL 通过 SQLAlchemy ORM / 参数化查询执行，禁止拼接用户输入

### 4.3 权限控制与鉴权

- 使用 JWT 鉴权（`SECRET_KEY` / `JWT_ALGORITHM` / `JWT_EXPIRE_MINUTES`），Token 过期或篡改返回 401
- `ALLOW_ANONYMOUS` 控制匿名访问：开发默认 `true`；生产如需强制鉴权，应先具备 Token 签发/注入方案
- **当前产品无账号密码体系、无登录接口、无密码哈希存储**；如后续引入账号登录，必须使用 bcrypt/argon2 等加盐哈希
- 角色权限（RBAC）为后续规划，当前按最小权限原则限制网络与数据库账号

### 4.4 跨域（CORS）

- 生产环境 `CORS_ORIGINS` 仅列可信前端源（逗号分隔），如 `https://linkmind.example.com`
- `allow_credentials=true` 时**禁止**使用 `*`，否则浏览器会拒绝带凭据请求
- 非白名单源预检应被拒绝且不返回 `Access-Control-Allow-Origin`

### 4.5 错误处理

- 避免暴露系统内部信息
- 使用统一的错误响应格式
- 记录详细的错误日志
- 错误信息脱敏处理

## 五、网络安全

### 5.1 网络隔离

- 生产环境与开发环境隔离
- 使用防火墙限制网络访问
- 数据库服务仅允许内部访问
- API 服务使用反向代理

### 5.2 访问控制

- API 使用 JWT 鉴权（`Authorization: Bearer <token>`），匿名开关由 `ALLOW_ANONYMOUS` 控制
- 限制单 IP 请求频率（可在 nginx / 网关层配置）
- 异常请求自动封禁
- 定期审计访问日志

### 5.3 DDoS 防护

- 配置请求速率限制
- 使用 CDN 分发流量
- 部署 WAF（Web 应用防火墙）
- 监控异常流量模式

## 六、代码安全

### 6.1 代码审查

- 所有代码提交必须经过代码审查
- 使用静态代码分析工具
- 检查安全漏洞和代码质量
- 遵循安全编码规范

### 6.2 依赖安全

- 定期更新项目依赖
- 监控依赖安全漏洞
- 使用 `npm audit` 和 `pip-audit` 检查漏洞
- 移除未使用的依赖

### 6.3 密钥管理

- 敏感配置使用环境变量
- 密钥存储在安全的密钥管理服务中
- 禁止在代码中硬编码密钥
- 定期轮换密钥

## 七、部署安全

### 7.1 Docker 安全

- 使用官方基础镜像
- 最小化镜像大小（使用 slim 版本）
- 以非 root 用户运行容器
- 限制容器网络权限

### 7.2 环境配置

| 环境 | 安全要求 |
|------|----------|
| 开发环境 | 可使用默认配置，数据持久化在本地 PostgreSQL；`ALLOW_ANONYMOUS=true` 便于联调 |
| 测试环境 | 使用独立数据库与独立 `KNOWLEDGE_ROOT`，模拟生产配置 |
| 生产环境 | `SECRET_KEY` ≥32 字节高熵随机值；`CORS_ORIGINS` 仅列可信源且禁止与凭据搭配 `*`；`ALLOW_ANONYMOUS` 按鉴权方案确认；启用 HTTPS 与所有安全措施 |

> 生产环境变量模板见 `deploy/.env.example`；容器内不读取 `backend/.env`，JWT/CORS/`DATABASE_URL` 必须由 compose 注入。

### 7.3 证书管理

- 使用有效的 SSL 证书
- 证书到期前及时更新
- 使用 Let's Encrypt 自动续期
- 证书私钥安全存储

## 八、日志与监控

### 8.1 日志记录

- 记录所有关键操作
- 记录 API 请求和响应
- 记录错误和异常信息
- 日志文件定期轮转

### 8.2 监控告警

- 监控系统性能指标
- 监控安全事件
- 异常情况自动告警
- 定期安全审计

### 8.3 安全事件响应

- 建立安全事件响应流程
- 定义事件级别和响应时间
- 及时通报安全事件
- 事件处理后复盘总结

## 九、安全检查清单

### 9.1 开发阶段

- [ ] 输入验证是否完整（Pydantic 模型）
- [ ] 是否全部使用 SQLAlchemy 参数化查询/ORM
- [ ] 文件/Git 操作是否限制在 `KNOWLEDGE_ROOT` 内
- [ ] Git 子进程是否使用 `shell=False` 参数列表
- [ ] 是否有敏感数据（密钥、数据库口令、Token）硬编码
- [ ] 依赖是否有已知漏洞

### 9.2 部署阶段

- [ ] 是否启用 HTTPS
- [ ] `SECRET_KEY` 是否 ≥32 字节且非仓库默认值
- [ ] PostgreSQL 账号是否为最小权限、密码是否安全
- [ ] `CORS_ORIGINS` 是否为显式可信源（未与凭据模式搭配 `*`）
- [ ] 是否限制网络访问（8000/5432 不暴露公网）
- [ ] 是否配置防火墙规则

### 9.3 运行阶段

- [ ] 是否定期备份数据
- [ ] 是否监控安全事件
- [ ] 是否定期更新依赖
- [ ] 是否定期安全审计

## 十、安全事故处理流程

```
安全事件发现
    ↓
事件级别评估
    ↓
启动响应流程
    ↓
隔离受影响系统
    ↓
调查事件原因
    ↓
修复安全漏洞
    ↓
恢复系统服务
    ↓
事件复盘总结
    ↓
更新安全策略
```

## 十一、安全责任

| 角色 | 安全职责 |
|------|----------|
| 开发人员 | 编写安全代码，进行安全测试 |
| 运维人员 | 部署安全配置，监控系统安全 |
| 安全负责人 | 制定安全策略，处理安全事件 |
| 管理员 | 管理用户权限，审核安全配置 |

## 十二、安全培训

- 定期进行安全意识培训
- 培训内容包括安全编码规范
- 培训内容包括安全最佳实践
- 培训后进行考核评估

## 十三、合规性

### 13.1 法律法规

- 遵守《网络安全法》
- 遵守《数据安全法》
- 遵守《个人信息保护法》
- 遵守 GDPR（如适用）

### 13.2 行业标准

- 参考 ISO 27001 信息安全管理体系
- 参考 OWASP Top 10 安全风险
- 参考 NIST 网络安全框架
