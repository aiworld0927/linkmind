# LinkMind 概要设计

> 本文给出页面、模块、领域模型、Git 能力映射与主要流程。字段、路径、表名均以当前代码为准。

## 一、前端页面与路由

路由定义在 `frontend/src/App.tsx`，使用 `HashRouter`：

| 路由 | 页面组件 | 职责 | 当前状态 |
|------|----------|------|----------|
| `#/` | `HomePage` | 展示知识地图卡片；按标题/描述搜索；新建、编辑、删除地图；进入脑图；跳转 Git 管理 | 已实现 |
| `#/map/:datasetId` | `MindMapPage` | 读取 `datasetId`，切换 store 中的活动数据集；无效 ID 显示 404 并提供返回首页；组合工具栏、面包屑、X6 画布、节点弹窗/抽屉、操作日志 | 已实现 |
| `#/git` | `GitPage` | 仓库登记与选择、刷新、拉取、推送、移除；变更勾选提交、冲突解决、合并继续/放弃；查看提交历史与 Git 动作审计 | 已实现 |
| `#/note` | `NotePage` | 从查询参数读取 `title`、`node`、`md`，渲染 Markdown 正文、文档大纲与滚动高亮；无内容时返回空态 | 已实现 |

未匹配路由重定向到 `#/`。`App.tsx` 还负责：

- `ConfigProvider` 中文语言包与主题；
- `ErrorBoundary` 包裹路由；
- 启动时执行 `bootstrap()` 恢复本地会话或内置示例数据；
- 注册 `window.linkmind`（`version/load/snapshot/reset`）；
- 读取 `window.__LINKMIND_DATA__` 进行宿主注入。

`NoteList` 的「查看」按钮把笔记拼成 Markdown 文本（标题、正文、标签、创建时间），通过 `navigate('/note?...')` 打开阅读页；在 HashRouter 下实际地址为 `#/note?title=&node=&md=`。

## 二、前端模块与状态管理

### 2.1 画布 store（`frontend/src/store/index.ts`）

| 维度 | 内容 |
|------|------|
| 数据 | `datasets`、`activeDatasetId`、`rootNodes`、`currentNodes`、`currentLevelId`、`breadcrumbs`、`levelHistory` |
| 视图 | `globalDisplayMode`、`canvasView`、`searchKeyword`、`popoverVisibleNodeId`、`drawerVisible`、`drawerTargetNodeId`、`logVisible`、`nodePositions` |
| 可追溯 | `operationLog`（上限 100 条）、`undoStack`（上限 30 层） |
| 控制器 | `canvasController`：画布注册 `fit/center/zoom/relayout`，工具栏消费 |
| 持久化 | 通过 `CanvasDataSource` 抽象写入 `localStorage`，key `linkmind_canvas_data`，`storageVersion=2`；写操作立即落盘，视图变化 400ms 防抖落盘 |
| 业务能力 | 数据集 CRUD、节点 CRUD、笔记 CRUD、依赖增删改（循环检测）、下钻/面包屑回退、撤销、导入导出 |

数据流：

```
组件事件 → store action → 校验 → set(...) → persist() → CanvasDataSource.save()
                                         └→ operationLog / undoStack
```

`MindMapPage` 只负责 URL 与 store 的同步；节点与笔记的读取通过 `currentNodes` 派生，避免页面自行维护副本。

### 2.2 Git store（`frontend/src/features/git/store.ts`）

| 字段/方法 | 说明 |
|-----------|------|
| `repos`、`currentId` | 仓库列表与当前仓库 |
| `loading`、`busy`、`error` | 首屏加载、单动作互斥、错误文本 |
| `load/select/refresh` | 列表加载、切换、单仓库刷新 |
| `addRepo/removeRepo` | 登记与移除登记 |
| `commit/pull/push` | 提交、拉取、推送 |
| `resolveConflict/continueMerge/abortMerge` | 冲突解决与合并生命周期 |

- 所有写操作统一经 `run(label, task)`：已有 `busy` 时直接返回，防止并发点击；异常转 `message.error`。
- 后端成功返回最新 `GitRepo`，`applyRepo` 原位替换并切换 `currentId`，因此无需二次请求。
- Git store 不持久化 localStorage，数据完全来自 `/api/v1/git/*`，不回退假数据。

### 2.4 API 客户端（`frontend/src/features/git/api.ts`）

- 基址 `/api/v1`，统一解析 `{code, msg, data}`；仅 `code === 200` 视为成功。
- 网络不可达抛 `ApiError('无法连接后端服务，请确认服务已启动', 0)`；非 JSON 响应抛格式异常。
- 提供 12 个 Git 方法以及 `listDirs`（调用 `/fs/dirs`）。

## 四、领域模型

PostgreSQL 共 10 张表，DDL 见 `backend/migrations/001_init.sql`，ORM 见 `models/db_models.py`。

| 表 | 主键 | 关键字段 | 关键约束/索引 |
|----|------|----------|----------------|
| `knowledge_repository` | `id uuid` | `name varchar(120)`、`fs_path varchar(1024)`、`git_remote`、`default_branch`、`last_synced_at` | 唯一 `name`、唯一 `fs_path`；`created_at/updated_at` |
| `knowledge_map` | `id uuid` | `repository_id` FK、`title varchar(160)`、`description`、`source_path`、`git_status` | 唯一 `(repository_id,title)`；索引 `ix_knowledge_map_repository`；仓库删除 `SET NULL` |
| `map_node` | `id uuid` | `map_id` FK、`parent_id` 自引用、`name`、`path`、`depth`、`sort_order`、`is_expanded`、`display_mode` | 地图删除级联；`ck_map_node_display_mode`；`ix_map_node_tree(map_id,depth,sort_order)`；根/子节点部分唯一索引 |
| `node_property` | `id uuid` | `node_id` FK、`label`、`content`、`tags text[]`、`remark`、`document_path`、`sort_order` | 节点删除级联；`ix_node_property_node`；GIN `ix_node_property_tags`；全文 GIN `ix_node_property_search` |
| `document` | `id uuid` | `repository_id` FK、`relative_path`、`title`、`content`、`checksum`、`git_status` | 唯一 `(repository_id,relative_path)`；`ix_document_repo_status`；全文 GIN `ix_document_search`；仓库删除级联 |
| `node_document_link` | `(node_id,document_id)` | `created_at` | 双向级联删除 |
| `node_link` | `(source_node_id,target_node_id)` | `created_at` | 双向级联；`ck_node_link_not_self`；`ix_node_link_target` |
| `operation_audit` | `id bigserial` | `map_id` FK、`actor`、`action`、`target_type`、`target_id`、`summary`、`payload jsonb` | 地图删除 `SET NULL`；`ix_operation_audit_map_time`；BRIN `ix_operation_audit_time_brin` |
| `git_action` | `id bigserial` | `repository_id` FK、`action`、`message`、`files jsonb`、`ok`、`detail` | 仓库删除级联；`ix_git_action_repo_time(repository_id,created_at DESC)` |
| `document_embedding` | `document_id` PK/FK | `model`、`embedding vector(1536)`、`updated_at` | 文档删除级联；ivfflat `ix_document_embedding_vector`，`lists=100`，余弦距离 |

领域对象关系：

```
knowledge_repository 1─n knowledge_map 1─n map_node 1─n node_property
                                                │
                                                ├─n node_document_link n─1 document
                                                └─n node_link (source/target 自引用)
knowledge_repository 1─n git_action
document 1─1 document_embedding
```

当前实际读写：`knowledge_repository` 与 `git_action` 由 Git 模块使用；其余表为已完成 DDL/ORM 的基线，尚未接入业务读写。

## 七、主要业务流程

### 7.1 登记知识仓库

1. 前端打开 `RepoDialog`，调用 `GET /fs/dirs?path=` 浏览 `KNOWLEDGE_ROOT` 内目录。
2. 用户填写名称，选择相对目录，可选填写远端地址与「初始化仓库」。
3. `POST /git/repos` 进入 `GitRegistryService.create_repo()`。
4. 校验名称（去空格、非空、≤120）；按名称查重，重复返回 409。
5. `resolve_repo_path()` 解析到 `KNOWLEDGE_ROOT` 内，校验存在且为目录；按相对路径查重，重复返回 409。
6. `GitService.is_repo()` 判断；不是仓库且未勾选初始化则返回 400；否则执行 `git init -b main`，目录中已有文件时生成「初始化知识仓库」提交。
7. 若提供 `remote_url`，`git remote add/set-url origin`。
8. 写入 `knowledge_repository`，提交事务，返回最新仓库视图。

### 7.2 提交

1. 前端校验提交信息非空、选中文件非空（全量提交除外）。
2. `POST .../commit`，Pydantic 校验 `message` 长度 1–500，且必须 `all=true` 或 `paths` 非空。
3. `_execute()` 获取仓库行与真实路径，进入该仓库的 `asyncio.Lock`。
4. `GitService.commit()`：若存在冲突直接抛 409；`all` 执行 `git add -A`，否则逐个路径安全校验后 `git add -- <paths>`。
5. `git diff --cached --quiet` 判断暂存区；无变更抛 400「没有可提交的变更」。
6. `git commit -m <message>`，成功后写入 `git_action`（`ok=true`），提交事务。
7. 返回最新视图与「提交完成」。

### 7.3 拉取产生冲突到解决

1. `POST .../pull`：先 `git rev-parse @{u}` 校验上游，再 `git fetch --prune`，最后 `git merge --no-edit <upstream>`。
2. 合并返回 0：根据输出返回「已是最新版本」或「拉取完成」。
3. 合并失败且 `status.conflicts` 非空：返回成功响应，消息「拉取产生冲突，请解决后完成合并」；审计中因消息含「冲突」记 `ok=false`。
4. 视图重新读取 `conflicts()`：`ours` 取 `:2:path`，`theirs` 取 `:3:path`，`working` 读工作区，均受 256KB 截断。
5. 前端 `ConflictPanel` 展示冲突；用户选择保留本地/远端，或编辑合并结果后提交 `content`。
6. `resolve_conflict()` 再次校验路径属于当前冲突集合；`ours/theirs` 在对应 stage 不存在时 `git rm -f`，否则 `git checkout --ours/--theirs`，随后 `git add -- path`。
7. 所有冲突解决后 `POST .../merge/continue`：检查 `MERGE_HEAD` 存在、无剩余冲突，执行 `git commit --no-edit`。
8. 或 `POST .../merge/abort`：检查 `MERGE_HEAD` 存在，执行 `git merge --abort`。

### 7.4 失败审计

1. `_execute()` 捕获 `BusinessError`（含 `GitError/NotFoundError/ConflictError`）。
2. 写入 `git_action`：`ok=false`，`message=exc.message`，`detail=exc.message`，`files` 为本次涉及文件（提交时仅非全量提交携带）。
3. 提交事务后重新抛出异常，由 `exception_handler` 转换为 `{code: <status>, msg: <message>}`。
4. 业务校验失败发生在 `_execute()` 之前时（如仓库不存在、路径不存在），不会产生 `git_action` 记录。
