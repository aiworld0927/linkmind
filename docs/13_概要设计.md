# LinkMind 概要设计

> 本文给出页面、模块、领域模型、Git 能力映射与主要流程。字段、路径、表名均以当前代码为准。
> 数据库细节见 [19_数据库设计.md](./19_数据库设计.md)，接口契约见 [15_API接口列表.md](./15_API接口列表.md)。

## 一、前端页面与路由

路由定义在 `frontend/src/App.tsx`，使用 `HashRouter`：

| 路由 | 页面组件 | 职责 | 当前状态 |
|------|----------|------|----------|
| `#/` | `HomePage` | 展示知识地图卡片；按关键词搜索；新建、编辑、删除地图；导入/导出；进入脑图；跳转 Git 管理 | 已实现 |
| `#/map/:mapId` | `MindMapPage` | 读取 `mapId`，从后端加载整树；无效 ID 显示空态并提供返回首页；组合 SVG 画布、侧边属性抽屉、右键菜单、操作日志 | 已实现 |
| `#/git` | `GitPage` | 仓库登记与选择、刷新、拉取、推送、移除；变更勾选提交、冲突解决、合并继续/放弃；查看提交历史与 Git 动作审计 | 已实现 |
| `#/note` | `NotePage` | 从查询参数读取笔记内容（`title`、`node`、`md`），渲染 Markdown 正文、文档大纲与滚动高亮；支持 Vditor 编辑 | 已实现 |

未匹配路由重定向到 `#/`。`App.tsx` 还负责：

- `ConfigProvider` 主题与中文语言包；
- `HashRouter` 路由壳与顶栏（首页/Git/脑图工具）；
- 启动时调用 `loadMaps()` 从后端加载地图列表；
- 全局挂载 `Modals`（地图/节点/属性/导入/仓库弹窗）。

数据全部来自 `/api/v1`；页面刷新后重新向后端拉取，不依赖 `localStorage`。

## 二、前端模块与状态管理

### 2.1 画布 store（`frontend/src/store/index.ts`）

| 维度 | 内容 |
|------|------|
| 数据 | `maps`、`activeMapId`、`collapsed`、`selectedId` |
| 视图 | `view(k,x,y)`、`searchKeyword`、`sideOpen`、`ctxMenu`、`modal`、`logOpen` |
| 可追溯 | `log`（操作记录，上限 200 条） |
| 加载状态 | `mapsLoading/mapsError`、`treeLoading/treeError` |
| 持久化 | 无 localStorage；地图/节点/属性/笔记均通过 API 落库到 PostgreSQL |
| 业务能力 | 地图 CRUD、导入/导出、节点 CRUD、属性 CRUD、笔记保存、整树加载与刷新 |

数据流：

```
组件事件 → store action → mindmapApi.* → utils/http.request()
        → 后端落库 → 返回 MapOut/TreeNodeOut → 更新 store 缓存 → 组件重渲染
        └→ logOp() 记录操作日志
```

`MindMapPage` 只负责 URL 与 store 的同步；整树通过 `ensureTree(mapId)` 从后端加载，避免页面自行维护副本。

### 2.2 Git store（`frontend/src/features/git/store.ts`）

| 字段/方法 | 说明 |
|-----------|------|
| `repos`、`currentId` | 仓库列表与当前仓库 |
| `loading`、`busy`、`error` | 首屏加载、单动作互斥、错误文本 |
| `load/select/refresh` | 列表加载、切换、单仓库刷新 |
| `addRepo/removeRepo` | 登记与移除登记 |
| `commit/pull/push` | 提交、拉取、推送 |
| `resolveConflict/continueMerge/abortMerge` | 冲突解决与合并生命周期 |

- 所有写操作统一经 `run(label, task)`：已有 `busy` 时直接返回，防止并发点击；异常转 `message.error`。
- 后端成功返回最新 `GitRepo`，`applyRepo` 原位替换并切换 `currentId`，因此无需二次请求。
- Git store 不持久化，数据完全来自 `/api/v1/git/*`，不回退假数据。

## 四、领域模型

PostgreSQL 共 **5 张业务表**，DDL 见 `backend/alembic/versions/0001_baseline.py`（等价脚本 `backend/migrations/001_init.sql`），ORM 见 `api/v1/git/models.py` 与 `api/v1/mindmap/models.py`；完整字段见 [19_数据库设计.md](./19_数据库设计.md)。

| 表 | 主键 | 关键字段 | 关键约束/索引 |
|----|------|----------|----------------|
| `git_repos` | `id uuid` | `name varchar(120)`、`fs_path varchar(1024)`、`remote_url`、`created_at/updated_at` | 唯一 `name`、唯一 `fs_path` |
| `git_actions` | `id uuid` | `repo_id` FK、`ts`、`action varchar(40)`、`message text`、`files jsonb`、`ok bool` | FK `ON DELETE CASCADE`；`ix_git_actions_repo_id` |
| `maps` | `id uuid` | `title varchar(30)`、`desc varchar(80)`、`repo_id` FK 可空 | 唯一 `title`；仓库删除 `SET NULL` |
| `nodes` | `id uuid` | `map_id` FK、`parent_id` 自引用可空、`name varchar(30)`、`sort_order` | 地图删除级联；`ix_nodes_map`；`ux_nodes_root_name`/`ux_nodes_child_name` 部分唯一 |
| `props` | `id uuid` | `map_id` FK、`node_id` FK 可空、`label`、`note_content`、`note_tags jsonb`、`note_remark`、`doc`、`doc_path` | 地图/节点删除级联；`ix_props_map_node` |

领域对象关系：

```
git_repos 1─n git_actions
git_repos 1─n maps            （repo_id 可空，ON DELETE SET NULL）
maps      1─n nodes           （ON DELETE CASCADE）
nodes     1─n nodes           （parent_id 自引用，ON DELETE CASCADE）
maps      1─n props           （ON DELETE CASCADE）
nodes     1─n props           （node_id 可空；NULL = 地图级属性，对应前端 ROOT）
```

说明：

- `maps` 行即前端脑图的“根节点（ROOT）”，ROOT 不单独建 `nodes` 行。
- 层级通过 `parent_id` 递归构建，不存储 `path`/`depth`；响应中的 `path` 由服务层拼接。
- 属性接口返回 `prop_id` 即 `props.id`；前端编辑/删除属性、读取/保存笔记均以 `prop_id` 定位。
- Git 运行时状态（branch/ahead/behind/merging/files/conflicts）不落库，实时执行 `git` 计算。

| 需求 | 后端实现 | 前端入口 |

| 放弃合并 | `POST .../merge/abort`：需存在 `MERGE_HEAD`，`git merge --abort` | 「放弃合并」 |
| 提交历史 | `GET .../log?page=&page_size=`，返回 `Page{total,items}` | 历史面板 |

## 七、主要业务流程

### 7.1 登记知识仓库

1. 前端打开 `RepoDialog`，调用 `GET /fs/dirs?path=` 浏览 `KNOWLEDGE_ROOT` 内目录。
2. 用户填写名称，选择相对目录，可选填写远端地址与「初始化仓库」。
3. `POST /git/repos` 进入 `GitRegistryService.create_repo()`。
4. 校验名称（去空格、非空、≤120）；按名称查重，重复返回 400。
5. `resolve_repo_path()` 解析到 `KNOWLEDGE_ROOT` 内，校验存在且为目录；按相对路径查重，重复返回 400。
6. `GitService.is_repo()` 判断；不是仓库且未勾选初始化则返回 400；否则执行 `git init -b main`，目录中已有文件时生成「初始化知识仓库」提交。
7. 若提供 `remote_url`，`git remote add/set-url origin`。
8. 写入 `git_repos`，提交事务，返回最新仓库视图。

### 7.2 提交

1. 前端校验提交信息非空、选中文件非空（全量提交除外）。
2. `POST .../commit`，Pydantic 校验 `message` 长度 1–500，且必须 `all=true` 或 `paths` 非空；失败返回 422。
3. 服务获取仓库行与真实路径，进入该仓库的 `asyncio.Lock`。
4. `GitService.commit()`：若存在冲突返回 400；`all` 执行 `git add -A`，否则逐个路径安全校验后 `git add -- <paths>`。
5. `git diff --cached --quiet` 判断暂存区；无变更返回 400「没有可提交的变更」。
6. `git commit -m <message>`，成功后写入 `git_actions`（`ok=true`），提交事务。
7. 返回最新视图与「提交完成」。

### 7.3 拉取产生冲突到解决

1. `POST .../pull`：先 `git rev-parse @{u}` 校验上游，再 `git fetch --prune`，最后 `git merge --no-edit <upstream>`。
2. 合并返回 0：根据输出返回「已是最新版本」或「拉取完成」。
3. 合并失败且 `status.conflicts` 非空：返回成功响应，消息「拉取产生冲突，请解决后完成合并」；审计中因消息含「冲突」记 `ok=false`。
4. 视图重新读取 `conflicts()`：`ours` 取 `:2:path`，`theirs` 取 `:3:path`，`working` 读工作区，均受 256KB 截断。
5. 前端 `ConflictPanel` 展示冲突；用户选择保留本地/远端，或编辑合并结果后提交 `content`。
6. `resolve_conflict()` 再次校验路径属于当前冲突集合；`ours/theirs` 在对应 stage 不存在时 `git rm -f`，否则 `git checkout --ours/--theirs`，随后 `git add -- path`。
7. 所有冲突解决后 `POST .../merge/continue`：检查 `MERGE_HEAD` 存在、无剩余冲突，执行 `git commit --no-edit`。
8. 或 `POST .../merge/abort`：检查 `MERGE_HEAD` 存在，执行 `git merge --abort`。

### 7.4 失败审计

1. 服务捕获 `AppException`（含 400/404/403）。
2. 写入 `git_actions`：`ok=false`，`message=exc.msg`，`files` 为本次涉及文件（提交时仅非全量提交携带）。
3. 提交事务后重新抛出异常，由 `core/exceptions.py` 转换为 `{code, msg, data: null}`，HTTP 状态码与 `code` 一致。
4. 业务校验失败发生在进入 Git 操作之前时（如仓库不存在、路径不存在），不会产生 `git_actions` 记录。
